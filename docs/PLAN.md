## 1. 프로젝트 개요

### 1.1 한 줄 정의

텍스트(나중엔 음성)로 지시하면, **PC를 조작**하고, **웹/문서를 찾아 근거와 함께 요약**하며, 대화·교정을 **D드라이브에 쌓아** 다음에도 더 맞게 응답하는 개인용 AI 에이전트.

### 1.2 로컬 모델과 하이브리드 검색

임베딩과 답변 생성은 로컬 Ollama, 재정렬은 로컬 ONNX 모델로 실행한다.
여기서 하이브리드 검색은 **키워드 검색과 벡터 검색의 결합**을 뜻한다.
외부 클라우드 LLM을 기본 두뇌로 쓰는 초기 구상은 D005의 로컬 전용 결정으로 대체되었다.

| 구성 | 현재 선택 | 역할 |
|---|---|---|
| 임베딩 | Ollama embeddinggemma | 문서·질문의 검색 벡터 |
| 검색 저장소 | SQLite FTS5 + sqlite-vec | 키워드·벡터 후보 검색 |
| 재정렬 | 로컬 MiniLM Cross-Encoder | 질문·후보 쌍의 관련성 평가 |
| 생성·주장 검사 | Ollama qwen3.5:9b | 검색 원문을 이용한 답변과 별도 검사 |
| 웹 검색 | DuckDuckGo | 허용된 외부 정보 요청에만 사용 |

로컬 문서 경로는 모델 설치 후 로컬에서 동작한다. 웹 검색은 네트워크가 필요하며,
전력·장치 비용이나 처리 지연이 없어지는 것은 아니다.

### 1.3 최종 사용자 경험 (v1)

1. 채팅창/단축키로 호출한다.
2. “메모장 열어”, “이 폴더 열어” 같은 단순 조종을 한다.
3. “OO 주제 찾아서 요약해줘” → 요약 + 링크를 받는다.
4. “말투는 짧게”, “이건 틀렸고 이게 맞아” → 다음 대화에 반영된다.
5. 마이크로 말해도 같은 일을 한다.

## 4. 전체 아키텍처

```
[키보드 / 마이크]
        │
        ▼
┌───────────────────┐
│  Input Layer      │  텍스트 입력 / STT(후반)
└─────────┬─────────┘
          ▼
┌───────────────────┐
│  Orchestrator     │  의도 파악 → 계획 → 도구 호출 → 관찰 → 반복
│  (Agent Loop)     │
└─────────┬─────────┘
          │
    ┌─────┼──────────┬──────────┬────────────┐
    ▼     ▼          ▼          ▼            ▼
 Memory  LLM Brain  Tools   Privacy Gate  Safety Gate
 (D:)    (Ollama)   (로컬)  (전송/마스킹)  (승인/권한)
    │     │          │          │            │
    └─────┴──────────┴──────────┴────────────┘
          ▼
┌───────────────────┐
│  Output Layer     │  화면 텍스트 / TTS(후반)
└───────────────────┘
          ▼
   Checkpoint / Session End → Summarizer → candidate memory
```

### 4.1 계층별 책임

| 계층 | 책임 | 실행 위치 |
|------|------|-----------|
| Input | 사용자 입력 수집 | 로컬 |
| Orchestrator | 도구 선택·루프·한도 관리 | 로컬 |
| LLM Brain | 이해·계획·요약·생성 | 로컬 Ollama |
| Memory | 저장·검색·세션 요약 | D:\Ai\Jarvis\data\memory |
| Tools | 실제 행동 | 로컬 |
| Privacy | 외부 전송 허용·마스킹·보존 정책 | 로컬 |
| Safety | 허용/거부/승인 | 로컬 |
| Output | 응답 표시·음성 | 로컬 |

### 4.2 질문 처리의 경로

입력·raw 기록·개인정보 처리 뒤 질문 목적에 맞게 분기한다.

| 경로 | 현재 처리 | 개선 |
|---|---|---|
| 문서 질문 | 표현 규칙/명시 `/search` → 하이브리드 검색·재정렬 → 원문 Evidence → Qwen 생성·근거 검사 | R3 질문 재작성·문맥/예산·모드 분리 |
| 일반 대화 | 허용된 최근 대화·미검증 회상 + 질문 → 로컬 Qwen | 문서 근거 없는 일반 답변 표시 정책 추가 |
| PC 명령·에이전트 | 기존 도구/계획 경로 → 인자·권한·승인 검사 → 실행·감사 | RAG 변경 시 기존 명령 회귀 보존 |

검색 결과에 들어 있는 명령은 실행 권한이 아니다. 결과 표시·음성·대화 저장은 각 모드의
근거/개인정보 정책을 따른다. 자동 대화 회상과 구조화 기억 lifecycle도 별도 계약이다.
정확한 현재/목표 연결은 [DESIGN 16장](DESIGN.md), 구현 순서는 Phase 3을 따른다.

## 5. 저장 구조 (D 드라이브)

소스는 `D:\Ai\Jarvis`, 현재 실행 데이터는 **`D:\Ai\Jarvis\data`**다(D025).
아래 트리는 통합한 실행 데이터 구조다. 자동 테스트는 별도 임시 폴더를 사용한다.
이전 운영·개발 데이터의 통합과 검증은 [통합 기록](DATA_CONSOLIDATION.md)에 정리했다.

```
D:\Ai\Jarvis\data\
├── config\
│   ├── settings.yaml        # 경로, 모델, 한도
│   ├── tools.yaml           # 허용 도구·인자·권한 화이트리스트
│   └── privacy.yaml         # 외부 전송, 보존, 마스킹 정책
├── memory\
│   ├── raw\                 # 대화 원문 (날짜/세션별)
│   ├── export\              # 기억 내보내기 결과
│   └── jarvis.sqlite3       # summaries/facts/corrections/task/검색 인덱스
├── docs\                    # RAG용 사용자 문서
├── skills\                  # 사용자 정의 스크립트/도구
├── state\                   # 실행 중 task, checkpoint, 복구 상태
├── logs\                    # 실행·도구·오류 로그
├── models\                  # (선택) Whisper, 로컬 LLM
└── backups\                 # 암호화 백업 staging (실제 사본은 별도 장치/위치)
```

개발용 `.env`가 필요하면 `D:\Ai\Jarvis\.env`에 두고 `.gitignore`에 등록한다. 운영 실행에서는 `.env` 대신 OS 보안 저장소를 사용한다.

### 5.1 저장 역할

| 저장소 | 내용 | 검색 우선순위 |
|--------|------|----------------|
| SQLite `kind=correction` | 사용자가 고친 정보 | 같은 key/주제 안에서 최우선 |
| SQLite `kind=fact` | 이름, 선호, 확정 사실 | 높음 |
| SQLite `kind=summary` | 세션 요약 | 중간 |
| `memory\raw\*.jsonl` | 원문 대화 | 낮음(복구·요약 시) |
| SQLite `documents/doc_chunks` | `docs\` 참고 문서 인덱스 | 질문 유형에 따라 |

### 5.2 세션 종료 시 저장 개념 (예시 필드)

```json
{
  "session_id": "ses_01J8Z9J0000000000000000",
  "summary": "사용자가 자비스 기억 구조와 검색 요약 방식을 논의함",
  "fact_candidates": [
    {"id": "fact_01J8Z9P00000000000000", "key": "pref.answer_style", "value": "짧고 근거 포함", "status": "candidate", "source_turn_id": "turn_01J8Z9K10000000000000"}
  ],
  "corrections": [],
  "tags": ["jarvis", "memory", "rag"],
  "raw_path": "memory/raw/ses_01J8Z9J0000000000000000.jsonl"
}
```

### 5.3 기억 레코드 스키마

Summarizer가 만든 사실은 바로 확정 기억이 아니라 `candidate`로 저장한다. 사용자가 `기억해:`로 직접 입력했거나 후보를 승인한 경우에만 `confirmed`가 된다.

```json
{
  "id": "fact_01J8Z9P00000000000000",
  "key": "pref.answer_style",
  "value": "짧고 근거 포함",
  "status": "confirmed",
  "source": {"session_id": "ses_01J8Z9J0000000000000000", "turn_id": "turn_01J8Z9K10000000000000", "kind": "user_explicit"},
  "created_at": "2026-08-10T20:30:00+09:00",
  "updated_at": "2026-08-10T20:30:00+09:00",
  "expires_at": null,
  "sensitivity": "normal",
  "supersedes": null,
  "tags": ["preference"]
}
```

필수 상태는 `candidate`, `confirmed`, `superseded`, `deleted`다. correction은 관련 없는 모든 fact보다 무조건 우선하지 않고, **같은 key/주제의 기존 레코드만** `superseded` 처리한다.

### 5.4 보존·삭제·복구 정책

- raw 로그: 기본 90일 보존 후 사용자 설정에 따라 삭제 또는 압축
- SQLite summaries/facts/corrections: 사용자가 목록 조회·수정·삭제·내보내기 가능
- 삭제: 본문·인덱스에 tombstone을 남기고, 백업은 보존 기간 만료 또는 재작성 시 함께 제거
- 쓰기: raw·설정은 임시 파일/append + flush, 상태 데이터는 처음부터 SQLite 트랜잭션 사용
- 복구: 시작 시 미완료 세션·부분 작성 파일을 탐지하고 자동 복구 결과를 로그에 남김
- 백업: `backups\`는 staging으로만 사용하고, 암호화된 사본을 별도 물리 장치 또는 별도 보안 위치에 보관하며 월 1회 복원 테스트 수행

## 7. 개발이 진행되는 전체 흐름

이 섹션은 **시간이 지날수록 제품이 어떻게 변하는지**를 설명한다.

### 7.1 큰 그림 (성숙 단계)

```
[레벨 0] 빈 프로젝트·설정
    ↓
[레벨 1] 말하는 챗봇 (저장만 함)
    ↓
[레벨 2] 기억하는 챗봇 (요약·facts)
    ↓
[레벨 3] 찾아주는 비서 (웹/문서 + 출처)
    ↓
[레벨 4] 손 있는 비서 (안전한 PC 조종)
    ↓
[레벨 5] 일 시키는 에이전트 (여러 도구 연결)
    ↓
[레벨 6] 말하는 자비스 (STT/TTS)
    ↓
[레벨 7] 상주형 비서 (트레이·단축키·알림)
```

### 7.2 사용자 입장에서 체감 변화

| 시점 | 사용자가 느끼는 변화 |
|------|----------------------|
| Phase 1 후 | “챗GPT처럼 대화되고, 기록이 파일로 남는다” |
| Phase 2 후 | “저번에 말한 선호를 다음에도 안다” |
| Phase 3 후 | “검색해서 링크와 함께 정리해 준다” |
| Phase 4 후 | “앱·폴더를 대신 열어 준다” |
| Phase 5 후 | “찾아 → 정리 → 저장을 한 번에 한다” |
| Phase 7 후 | “말로 시켜도 된다” |

### 7.3 개발자 입장에서 진행 방식

1. **수직 슬라이스:** 매 Phase마다 “작은 데모가 돌아가게” 만든다.
2. **게이트:** Phase 완료 기준을 통과하기 전에 다음 Phase로 넘어가지 않는다.
3. **회귀 테스트:** 12장의 고정 시나리오 중 현재 Phase까지 적용되는 항목을 매번 다시 돌린다.
4. **안전 기본값:** 새 도구는 기본 deny, 화이트리스트에 넣을 때만 allow.
5. **기억 품질:** 요약 자동화와 별도로, 중요 facts는 사용자 확정을 선호한다.

### 7.4 공부 로드맵과의 진행 동기화

| 공부 순서 | 개발 Phase | 연결 포인트 |
|-----------|------------|-------------|
| 1~3. 통계/뉴럴/트랜스포머 | Phase 0 전·병행 | 이론 (왜 LLM이 이렇게 동작하는지) |
| 4. 대화형 AI | Phase 1 | 프롬프트, 멀티턴, 환각 |
| 5. RAG | Phase 2~3 | 기억 검색, 웹/문서 근거 |
| 6. 추론·RL 개념 | Phase 5 전후 | 계획·도구 선택 이해 (필수 구현은 아님) |
| 7. AI 에이전트 | Phase 4~5 | 도구 호출 루프 |
| (응용) 음성 | Phase 7 | STT/TTS |

**추천:** 이론 1~3은 가볍게 병행하고, **학습 항목 4→5→7 순으로 구현 코드와 함께** 간다.

### Phase 2 — 기억 (세션 요약 + 다음 세션 활용)

**목표:** 컨텍스트가 끝나도 “나에 대한 정보”가 남는다

**작업**

- 세션 종료(`/bye`) 시 Summarizer 호출
- SQLite `records.kind`로 summary/fact/correction을 구분해 트랜잭션 저장
- Summarizer 결과는 `candidate`로 저장하고 자동 생성 confidence만으로 확정하지 않음
- `기억해:`는 `confirmed`, `틀림:`은 같은 key/주제의 기존 기억을 `superseded` 처리
- 새 세션 시작 시 관련 기억 top-k를 시스템 컨텍스트에 삽입
- 사용자 피드백 명령
  - `기억해: ...`
  - `틀림: (잘못된 내용) → (올바른 내용)`
- 기억 관리 명령: `/memory list`, `/memory confirm`, `/memory edit`, `/forget`, `/memory export`
- 정상 종료가 아니어도 마지막 체크포인트까지 요약 후보를 재생성할 수 있게 함
- 구조화 기억은 SQLite FTS5 trigram 검색을 사용한다. 문서·과거 대화의 임베딩 검색은 현재 별도 SemanticMemory 경로다(DESIGN 16장).

**진행 중 동작 흐름**

```
대화 중: raw에 계속 append
    ↓
/bye
    ↓
Summarizer(LLM) → summary + candidate facts
    ↓
명시적 `기억해:` 또는 사용자 승인 → confirmed
    ↓
다음 실행
    ↓
질문 key/FTS (이후 임베딩) → 관련 기억 검색 → 프롬프트에 포함 → 답변
```

**완료 기준**

- [ ] 종료 후 SQLite에 summary 레코드가 생긴다
- [ ] 재실행 후 “내 선호”를 묻지 않고도 반영한다
- [ ] correction이 같은 key의 이전 기억을 superseded 처리한다
- [ ] candidate 기억은 승인 전 일반 답변에 확정 사실처럼 사용되지 않는다
- [ ] `/forget` 후 해당 기억이 검색 인덱스에서도 제외된다

**주의**

- 요약이 틀리면 잘못된 기억이 고착될 수 있음
- 비밀번호·토큰·민감정보는 저장 금지 목록과 패턴 필터로 제외

**예상 기간:** 1~2주
**학습 연결:** RAG 입문 (검색·컨텍스트 주입)

### Phase 3 — 웹/문서 검색 → 요약 전달

**목표:** “모델 머릿속”이 아니라 “찾아서” 답한다

**작업**

- Web Search 도구 1개 연동
- 웹/문서 본문은 모두 **신뢰할 수 없는 데이터**로 표시하고 그 안의 명령문은 실행 지시로 취급하지 않음
- 외부 콘텐츠가 시스템 프롬프트·사용자 의도·도구 권한을 변경할 수 없도록 Orchestrator에서 신뢰 경계 강제
- 응답 포맷 고정
  1. 핵심 요약
  2. 주장별 근거 링크와 확인 날짜 (필수)
  3. 상태: `근거 확인` / `상충` / `근거 부족`
- 출처 내용과 적용 조건으로 판단; 출처 수로 확실성을 부여하지 않음
- `docs\` 로컬 RAG (문서 준비 → 질문 구성·벡터화 → 검색·재정렬 → 근거 기반 생성·검사)

- Web fetcher는 `http/https`만 허용하고 redirect 횟수·본문 크기·timeout 제한; loopback, 사설 IP, `file:` 및 사용자 정의 프로토콜 차단
- 문서별 `local_only`/`api_allowed` 전송 등급과 전송 전 민감정보 마스킹

**완료 기준**

- [ ] 검색 질문에 URL이 답변에 포함된다
- [ ] 검색 실패 시 솔직히 실패를 말한다
- [ ] 로컬 문서 질문 시 파일명/인용을 보여준다
- [ ] 악성 웹/문서의 “이전 지시 무시·도구 실행” 문구가 도구 호출로 이어지지 않는다
- [ ] `local_only` 문서 원문이 외부 API 요청에 포함되지 않는다
- [ ] 각 핵심 주장과 출처를 역추적할 수 있다

**예상 기간:** 1~2주
**학습 연결:** RAG 시스템

### Phase 5 — 에이전트 루프 (일 시키기)

**목표:** 여러 도구를 순서대로 연결한다

**작업**

- Agent loop 구현
  - Decide(tool 또는 final) → Validate → Act → Observe → (repeat) → Final Answer
  - 내부 추론 원문은 저장하지 않고 사용자에게 보여줄 짧은 작업 계획·도구 호출·결과만 기록
- `max_steps` (예: 6~8)로 무한 루프 방지
- `task_id`와 단계별 상태(`pending/running/succeeded/failed`) 저장, 재시작 시 중복 실행 방지
- 재시도는 검색 등 안전하고 idempotent한 동작만 허용; 파일 쓰기·외부 변경은 자동 재시도 금지
- 웹/문서의 지시는 새 사용자 의도로 승격하지 않으며, 각 부작용 단계는 원래 사용자 요청과 다시 대조
- 복합 태스크 예
  - “주제 검색 → 요약 → `docs\notes\`에 저장 → 폴더 열기”
- 실패 시 완료된 단계·실패 단계·미실행 단계를 구분해 보고

**완료 기준**

- [ ] 단일 지시로 검색+저장이 이어진다
- [ ] step 한도 초과 시 안전하게 멈춘다
- [ ] 중간 실패가 로그와 사용자 메시지에 남는다
- [ ] 강제 종료 후 재개해도 완료된 쓰기 작업이 중복 실행되지 않는다
- [ ] 검색 결과에 포함된 명령이 사용자 승인 없이 새 작업을 만들지 않는다

## 9. 기억·피드백·성장 방식

### 9.1 “성장”의 의미

이 프로젝트에서 성장은 **모델 가중치가 커지는 것**이 아니라,

- 나에 대한 **기억(facts)** 이 늘고
- **교정(corrections)** 이 쌓이며
- 검색·규칙이 나아져

**다음 유사 질문에 더 맞게 답하는 것**을 의미한다.

### 9.2 피드백이 저장되는 경로

| 사용자 행동 | 저장 위치 | 다음 효과 |
|-------------|-----------|-----------|
| 일반 대화 | raw JSONL → 종료 시 SQLite summary | 맥락 유지 |
| `기억해: ...` | SQLite fact | 선호/사실 반영 |
| `틀림: A → B` | SQLite correction | 오답 재발 감소 |
| 좋아요/싫어요(선택) | 로그/통계 | 규칙·프롬프트 조정 재료 |

### 9.3 되지 않는 것

- API 제공 모델 자체가 당신 피드백으로 재학습되지 않음
- 저장만 하고 검색하지 않으면 “기억한 척”만 하고 다음엔 못 씀

### 9.4 잘 되게 하는 규칙

1. 먼저 질문과의 관련성을 계산하고, **같은 key/주제 안에서만** correction > confirmed fact > summary > raw 순으로 우선한다.
2. `candidate`는 확정 사실처럼 답변에 사용하지 않고, 중요 사실은 **사용자 확정**을 거친다.
3. 모든 기억은 출처 세션·턴과 생성/수정 시각을 보존한다.
4. 민감정보는 저장·API 전송·로그·TTS 각각에서 독립적으로 차단한다.
5. 새 correction은 이전 레코드를 삭제하지 않고 `superseded`로 연결해 변경 이력을 남긴다.
6. 사용자는 기억을 언제든 조회·수정·삭제·내보낼 수 있다.

## 10. 정보 신뢰성 (검색·요약 검증)

완전 자동 “진실 판별기”는 없다. 아래 절차로 **신뢰 가능한 전달**을 만든다.

1. **출처 동봉:** 요약 + URL/문서명/인용
2. **근거 검사:** 원문이 주장을 지지하는지 확인하고 검색된 자료의 상충을 검사; 출처 수는 확실성 기준이 아님
3. **원문 대조:** 검색 결과에 없는 내용은 단정 금지
4. **최신성:** 날짜가 중요한 주제는 작성 시점 표시
5. **상태 라벨:** 근거 확인 / 상충 / 근거 부족
6. **고위험 주제:** 의료·법률·금융·보안은 1차 출처 직접 확인 권고
7. **중요 행동 전 승인:** 검색 결과를 바탕으로 한 시스템 변경은 항상 확인
8. **신뢰 경계:** 웹·메일·문서·도구 출력에 포함된 명령은 사용자 또는 시스템 지시로 취급하지 않음
9. **주장-근거 연결:** 핵심 주장마다 실제로 그 주장을 뒷받침하는 출처와 확인 날짜를 연결
10. **도구 권한 분리:** 검색 결과는 도구 호출의 인자로 자동 승격하지 않고 원래 사용자 의도와 정책을 다시 검증

## 11. 안전·권한 설계

### 11.1 기본 원칙

- 기본 거부, 명시적 허용만 실행
- 설명 가능한 로그
- 위험도에 따른 인간 승인
- 쓰기 경로 제한
- 웹/문서/도구 출력은 권한 없는 데이터로 취급
- 승인은 도구명·정규화된 인자·대상·예상 변경에 결합하고 변경되면 무효화
- 승인 UI에는 실행 직전 값만 표시하며, LLM이 만든 설명만 믿지 않고 정책 엔진이 계산한 대상을 표시

### 11.2 위험 등급 예시

| 등급 | 예 | 정책 |
|------|----|------|
| Low | 허용 앱 실행, 폴더 열기 | 자동 |
| Medium | 허용 경로의 새 파일 생성, 미등록 도메인 열기 | 정확한 대상 표시 후 확인 |
| High | 등록 skill 실행, 덮어쓰기, 설치, 시스템 설정 | 확인 문구 입력 + v0.5 기본 비활성 가능 |
| Forbidden | 삭제·포맷·임의 셸·보안 설정 해제 | v1에서는 승인 여부와 무관하게 차단 |

### 11.3 실행 금지 (v1)

- 임의 파일/디렉터리·디스크 삭제 및 포맷 (`/forget`은 memory 전용 안전 삭제 경로로 별도 구현)
- 비밀번호·결제·계정 권한 변경
- 출처 불명 프로그램 다운로드 후 실행
- 사용자 홈 전체·시스템 디렉터리 무단 탐색·수정

## 로컬 의미 검색 확장 (2026-10-13)
문서 검색의 특징 해싱을 로컬 embeddinggemma 임베딩으로 교체하고 FTS5/RRF는 유지한다.
질문·답변 쌍의 영구 저장·검색을 추가한다. sqlite-vec는 별도 서버 없이 사용하며,
임베딩 장애 시 FTS5로 동작한다. 모델 재학습은 제외한다. 과거 로그 가져오기는 별도 명시적 스크립트로 제공하며 자동 실행하지 않는다.
완료 기준은 재시작 후 검색, 문서 변경·삭제, 모델 변경 격리, 장애 복구, 시크릿 차단 테스트다.

현재 구현: 문서·대화 RRF 후보에 로컬 ONNX Cross-Encoder 재정렬이 연결되어 있다.
모델 누락·추론 실패 시 RRF 순서를 보존하며 최종 개수 제한 전에 재정렬한다.
설치 및 운영 계약은 [로컬 의미 검색](post-v1/LOCAL_SEMANTIC_MEMORY.md)을 따른다.

### 답변 정책

근거가 있는 질문은 검색 원문으로 Qwen이 답변한다. 근거가 없는 일반 지식 질문은
“문서 근거 없는 일반 답변”으로 구분해 같은 로컬 모델에 요청한다.
회사 규정·개인 문서의 사실은 자료가 없으면 보류한다. 검색 오류나 상충을 일반 답변으로 덮지 않는다.
최신 웹 정보는 허용된 외부 검색으로 근거를 확보한다. 일반 답변을 문서 근거로 자동 축적하지 않는다.

### 범위 밖 또는 별도 결정

Office/OCR, 복잡한 PDF 레이아웃, 대규모 ANN, 다중 사용자 권한·SSO, 모델 자체 학습은 이번 기본 개선과 분리한다.
청크 384토큰·이웃 반경 1·검색 시 5초 간격 확인을 D024의 개발 기본값으로 적용했다. 실무 자료 최적화는 별도다.
2026-10-15: 입력 목적에 따라 문서 등록과 질문 검색을 분리하고, 문서 청크를 `recursive-context-v3`로 교체했다.
텍스트 PDF 추출·여백 제거·법령 구조/페이지 보존·제목 전용 청크 제외를 추가했다(D012).
상세 변경·실제 PDF 검증은 [PDF 적용 보고](rag/RAG_PDF_INGESTION.md)를 따른다.
질문은 전체 임베딩하며 문서 크기 제한을 적용하지 않는다. 변경·검증은 [적용 보고](rag/RAG_RECURSIVE_CHUNKING.md)에 기록한다.
기존 20문서/200질문 검색 평가와 12개 답변 회귀는 개발 기준선이며 실무 정확도 보장이 아니다.
코드·설정 기본값·추가 색인 테이블을 적용했다. 운영 DB 강제 전환과 정식 릴리스 게이트 통과를 뜻하지 않는다.
