## 1. 한 줄 요약

`--voice`로 켰을 때만 마이크를 열고, "자비스"라고 부르면 깨어나서 한국어로 대화한다.
전부 로컬에서 처리하고, **음성으로는 위험한 작업을 승인할 수 없다.**

## 2. 게임으로 치면

보이스 채팅 시스템을 만드는 것과 거의 같다.

| 이 프로젝트 | 게임에서 같은 것 |
|-------------|------------------|
| 웨이크워드 "자비스" | 푸시투토크 대신 음성 감지(VAD) 활성화 |
| 마이크 게이트 | 노이즈 게이트 |
| 끼어들기(barge-in) | 상대 말 도중 끼어들기 |
| TTS 에코 문제 | 스피커 소리가 마이크로 다시 들어오는 문제 |
| AEC | 에코 캔슬레이션 |
| pre-roll 버퍼 | 링 버퍼로 앞부분 확보 (첫 음절 안 잘리게) |
| 마이크 인디케이터 | 보이스챗 말하는 중 아이콘 |

**스피커로 재생하면서 마이크로 듣는 문제**를 다루는 것이라, 보이스챗 개발 경험이 있으면
그 지식이 거의 그대로 적용된다.

## 3. 왜 엔진을 두 개 쓰나

| 용도 | 엔진 | 이유 |
|------|------|------|
| 호출어 감지 | Vosk 한국어 소형 모델 (CPU) | 항상 켜져 있어야 하니 가벼워야 함 |
| 질문 인식 | faster-whisper small (GPU) | 자유 발화 정확도가 필요 |
| 음성 출력 | Windows SAPI (Heami, 속도 4) | OS 내장. 외부 전송 0 |

이게 게임에서 **LOD(디테일 레벨)** 를 나누는 것과 같은 판단이다. 항상 도는 대기 상태는
가벼운 모델로, 실제로 필요한 순간에만 무거운 모델을 GPU에 올린다.

문서에 실제 시행착오가 기록되어 있다. Vosk 소형 모델 단독으로 자유 발화를 인식시켰더니
한국어 질문이 엉뚱한 문장으로 바뀌는 경우가 많았다. 그래서 용도를 쪼갰다.

Whisper를 `medium`이 아니라 `small`로 고른 이유도 명확하다. RTX 4070 Ti 12GB에서
Ollama 9B 모델과 **동시에** 올라가야 하기 때문이다. VRAM 예산 배분 문제다.

## 4. 상태 흐름

```text
Idle → WakeListening → "무엇을 도와드릴까요." → Recording
→ Transcribing → Orchestrator(channel=voice)
→ Speaking 또는 ApprovalWaiting → Idle
       └─ Speaking 중 "자비스" → TTS 중단 → 안내 → Recording
```

### 녹음과 재생을 절대 동시에 하지 않는다

동시에 하면 **자기 출력을 다시 입력으로 듣는 루프**가 생긴다. 보이스챗에서 스피커로 듣는
사람이 하울링을 만드는 것과 같다.

예외는 "끼어들기 감시" 하나인데, 그건 아래 5번에서 게이트를 겹겹이 쌓아서 처리한다.

## 5. 끼어들기 게이트 — 게임 오디오와 가장 닮은 부분

답변을 스피커로 읽는 중에 "자비스"라고 부르면 중단해야 한다. 문제는 **스피커 소리가 마이크로
다시 들어온다**는 것이다.

그래서 게이트를 3단으로 쌓았다.

```text
Speaking 중 마이크 입력
→ [Gate A] Speaking 전용 레벨 하한 (-32 dBFS)
→ [Gate B] 급격한 레벨 상승(onset) 검출 (기준창 대비 8dB 이상)
→ [Gate C] WebRTC VAD 사람 음성 판정
→ 통과한 프레임만 Vosk에 전달
→ "자비스" 감지 → TTS 중단
```

| 게이트 | 게임 오디오에서 같은 것 | 막는 것 |
|--------|-------------------------|---------|
| A | 노이즈 게이트 임계값 | TTS 잔향 |
| B | 트랜지언트/어택 검출 | 일정한 크기의 에코 |
| C | 음성 활동 감지 | 키보드 소리, 팬 소음 |

### Gate A: 질문 녹음보다 임계값을 높인다

질문 녹음은 `-42 dBFS`, 끼어들기는 `-32 dBFS`다. 끼어들기 쪽이 10dB 더 크다.

같은 값을 쓰면 스피커 잔향도 "큰 입력"으로 통과한다. 게임에서 상황별로 다른 노이즈 게이트
프리셋을 쓰는 것과 같다. **그리고 이 두 값을 절대 같이 만지지 않는다.** 끼어들기가 잘 안
된다고 질문 녹음 임계값을 낮추면, 질문 인식이 잡음을 먹기 시작한다.

### Gate B: 급상승만 사람으로 본다

매 프레임의 절대 크기만 보지 않고, **직전 기준창 중앙값보다 갑자기 8dB 이상 커진 구간**만
"사람이 말 시작"으로 본다.

TTS 에코는 일정한 크기로 계속 들어오지만, 사람 목소리는 갑자기 시작된다. 이게 어택 검출과
같은 아이디어다.

추가 규칙:

- TTS 재생 시작 후 첫 750ms는 게이트를 닫는다 (재생 시작 어택을 사람으로 오인하지 않게)
- onset 앞의 500ms를 메모리 pre-roll로 확보한다 (첫 음절 "자"가 안 잘리게)
- onset 밖의 오디오는 버리고 STT에 안 넣는다
- 게이트가 닫힐 때 Vosk 상태도 초기화한다

pre-roll은 게임에서 리플레이나 하이라이트 녹화를 위해 링 버퍼에 과거 몇 초를 계속 들고 있는
것과 정확히 같은 기법이다. 이벤트가 감지된 시점에는 이미 시작 부분이 지나갔기 때문이다.

### Gate C: VAD는 화자 인증이 아니다

문서가 명시적으로 경고하는 부분이다. WebRTC VAD는 "사람 목소리 같은 소리"를 구분할 뿐이고,
**TTS도 사람 목소리로 판정된다.** 그래서 VAD만으로는 사용자와 스피커를 구분하지 못한다.
Gate A(근거리 크기)와 Gate B(급상승)를 반드시 같이 써야 한다.

### AEC와 빔포밍은 왜 미뤘나

| 기술 | 미룬 이유 |
|------|-----------|
| AEC (에코 캔슬) | Windows SAPI가 스피커로 직접 재생해서, AEC에 필요한 "재생 중인 신호" 참조를 앱에 안 준다 |
| 빔포밍 | 현재 USB 콘덴서 마이크가 단일 채널이다. 빔포밍은 마이크 2개 이상과 배열 위치 정보가 필요 |

AEC는 "지금 스피커로 나가는 파형"을 알아야 마이크 입력에서 뺄 수 있다. 게임 엔진에서
오디오 믹서의 출력 버스를 참조할 수 있어야 하는 것과 같은데, SAPI는 그걸 안 준다.
실장치 테스트에서 목표 미달일 때만 다시 검토한다.

## 6. 호출 오인 문제와 해결

사용자가 보고한 실제 문제 4개와 해결 방식이다.

| 문제 | 원인 | 해결 |
|------|------|------|
| 아무 말이나 "자비스"로 인식 | Vosk 문법에 `[unk]`가 없어서 모델이 다른 말도 억지로 호출어에 맞춤 | 문법에 `[unk]` 추가 + 단독/접두만 인정 |
| 답변 중 재호출이 잘 안 됨 | 스피커 에코 | 위의 3단 게이트 + `ctrl+alt+j` 핫키 |
| "자비스 ○○ 알려줘"를 한 번에 말해도 다시 질문해야 함 | 항상 호출 → 안내 → 질문 순서로 고정 | 나머지 말이 있으면 안내 생략하고 바로 처리 |
| "자비스 가나다"가 "자비스 자비스"로 보임 | 호출 확정 후에도 제한 문법 Vosk에 계속 넣어서 후속 음절이 호출어로 강제 매핑 | 호출 확정 후 Vosk 중단, PCM만 Whisper로 |

### 첫 번째 문제가 특히 배울 점이 있다

Vosk에 "허용 문장은 `자비스`, `자 비스` 뿐"이라고 제한 문법을 줬다. 그러면 모델은 **모든
입력을 그 둘 중 하나로 맞추려 한다.** "안녕하세요"도 가장 가까운 `자비스`로 매핑된다.

`[unk]`(알 수 없는 발화)를 문법에 넣어야 "이건 둘 다 아님"이라는 답이 가능해진다.
게임으로 치면 enum에 `None`이나 `Invalid` 값을 안 넣어서 잘못된 입력이 첫 번째 값으로
들어가는 것과 같다.

### 네 번째 문제는 순서 버그다

호출이 확정된 다음에도 제한 문법 스트림에 계속 오디오를 넣으면, 뒤에 이어지는 "가나다"도
어휘 목록에서 가장 가까운 `자비스`가 된다. 그래서 **호출 확정 시점에 Vosk를 끄고** 이후
오디오는 Whisper에만 준다. 상태 전환 시 이전 상태의 처리를 확실히 끄는 것, 스테이트 머신
전환에서 자주 나오는 버그와 같다.

## 7. 품질 가드 — 못 알아들었으면 실행하지 않는다

Whisper 결과가 아래를 다 통과해야 AI에게 전달한다.

| 조건 | 기본값 |
|------|--------|
| 공백 제거한 문장이 비어 있지 않음 | — |
| 실제 음성 길이가 최소 길이 이상 | 400ms |
| 세그먼트 평균 log probability | -1.0 이상 |
| no-speech probability | 0.6 이하 |

실패하면 **추측해서 실행하지 않고** "잘 듣지 못했습니다. 다시 말씀해 주세요."라고 안내한다.

이게 이 Phase의 안전 원칙이다. 낮은 확신도의 인식 결과로 파일을 만들거나 앱을 실행하면
사용자가 의도하지 않은 일이 벌어진다. 게임에서 입력 판정이 애매할 때 아무 액션이나 발동하는
게 아니라 무입력으로 처리하는 것과 같다.

## 8. 음성이 보안을 약화시키지 않는다

| 규칙 | 이유 |
|------|------|
| high 위험 작업은 음성 승인 불가 | 음성은 위조·오인이 쉽다. 화면에서 문구를 타이핑해야 한다 |
| `--voice` 없이는 마이크를 안 연다 | 사용자 모르게 녹음하지 않는다 |
| 호출 전 오디오는 메모리에만 | 파일·외부 API로 안 보낸다 |
| 최종 답변만 읽는다 | 도구 원문·감사 로그·승인 토큰은 안 읽는다 |
| secret/pii_high는 낭독 거부 | 화면 전용 대체 문장으로 바꾼다 |
| 긴 답변은 요약만 읽는다 | 전체는 화면에 표시 |
| 같은 문장이면 음성·텍스트 결과가 같아야 함 | 채널에 따라 정책이 달라지면 안 됨 |

마지막 항목(parity)이 중요하다. 음성 경로에만 있는 예외를 만들면 그게 우회 경로가 된다.
Phase 4에서 "UI가 정책을 우회하는 예외 경로 금지"라고 한 것과 같은 원칙이다.

## 9. 튜닝 순서 (이거 하나만 기억하면 됨)

끼어들기가 잘 안 될 때 **모델을 바꾸기 전에** 이 순서로 확인한다.

1. `[끼어들기 마이크]` 표시에서 내 발화가 `-32 dBFS` 이상인가?
2. `VAD 음성`이라고 나오는데 `onset`이 안 뜨면 → `min_onset_rise_db`를 8에서 6으로만 낮춤
3. 음량 자체가 작으면 → Windows 입력 볼륨과 마이크 거리를 먼저 조정
4. 그래도 안 되면 → `speech_threshold_dbfs`를 `-35` 정도로
5. 오발동이 생기면 → 반대로 한 항목씩 올림

규칙: **한 번에 한 값만 바꾸고, 같은 문장 3개를 다시 말해서 전후를 비교한다.** 설정 변경 후엔
프로그램을 재시작해야 적용된다.

마이크는 입에서 15~30cm, Windows 입력 볼륨이 포화되지 않게. 이건 게임 오디오 튜닝과 똑같아서
파라미터를 여러 개 동시에 바꾸면 뭐가 효과였는지 알 수 없다.
