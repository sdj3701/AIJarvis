## 근거 처리 계약

1. `/search 질문`은 기본적으로 로컬 문서를 검색한다. 웹·인터넷·뉴스·날씨·최신 자료를
   요청하는 표현이 있으면 웹 검색도 시도한다. 사내·우리 회사·로컬·내부 문서·연차 등
   내부 질문은 웹으로 보내지 않는다. 예: `/search 웹 Ollama 최신 소식`.
   규칙 기반 라우팅이므로 기업용 접근권한 통제나 완전한 정보 유출 방지로 해석하지 않는다.
2. 내부 질문 키워드에 해당하면 '알려줘'가 없어도 검색한다. 다만 표현 규칙이므로 모든 내부
   질문을 잡지는 못한다. ‘출장 식비 한도가 얼마야?’와 후속 질문의 검색 누락은 R3-01 개선 대상이다.
3. 이번 검색에서 모델에 제공할 수 있는 마스킹된 자료에만 `S1`, `S2` 같은 ID를 부여한다.
   생성 모델은 JSON의 `status`, `claims`, `citations.source_id`, `citations.quote`로 답한다.
   Ollama `format`에 JSON Schema를 전달하며 출처 ID의 enum도 해당 검색 결과로 제한한다.
4. 인용 ID가 존재하고 인용문이 실제 원문에 포함되는지 검사한다. 공백 차이만 정규화한다.
   답변에 새로운 숫자가 추가되면 거부한다. `30000`과 `30,000`은 같은 수로 처리한다.
   원문 수치의 합산·단위 변환과 한글 수사 등은 이 검사에서 보수적으로 거부될 수 있다.
5. 유효한 초안만 별도 LLM 호출로 검사한다. 각 주장 전체의 근거, 질문 적합성, 부정·조건·
   숫자의 변경, 검색된 다른 문서와의 모순을 검토한다. 인용이나 검사가 실패하면 초안 전체를
   숨기고 보류한다. 오류·잘린 JSON·시간 초과·문맥 초과도 보류하며 원문 주장을 저장하지 않는다.
6. 화면에 쓰는 인용 번호와 파일/청크/URL은 앱이 실제 출처에서 구성한다. 검증 통과에
   사용된 출처만 `TurnOutcome.sources`에 남긴다. 보류 시 나오는 '검토할 검색 자료'는
   답변을 뒷받침하는 인용으로 간주하지 않는다.
7. 상태는 `근거 확인`, `상충`, `근거 부족`이다. `근거 확인`은 원문 일치 검사와 모델 검사를
   통과했다는 뜻이며 사실의 진실성 보장이 아니다. 출처가 하나여도 통과할 수 있고,
   출처가 여러 개여도 확실성을 부여하지 않는다. 기존 `require_min_sources` 설정은 호환성만
   유지하며 이 판단에 사용하지 않는다. 재정렬 logit 역시 사실성 점수가 아니다.
8. 검증 호출도 예산·토큰·응답 시간에 합산한다. `rag.grounding`은 상태·사유·출처 수만 기록한다.
   음성은 짧은 결론 또는 보류 사유를 전달하며 상세 영역에 출처와 발췌를 유지한다.

구조화 출력 API는 [Ollama 공식 문서](https://github.com/ollama/ollama/blob/main/docs/capabilities/structured-outputs.mdx)를 따른다.
생성·검증에 같은 로컬 모델을 사용하므로 두 모델의 독립 검증이나 확률적 신뢰도 보정은 아니다.

## 검색 평가

```powershell
.\.venv\Scripts\python.exe -m app.rag.benchmark.service --config-dir D:\Ai\Jarvis\data\config --dataset datasets/evaluation_queries.json --output-dir results\rag-current-20261014\retrieval-final --repeats 3
```

출력 경로는 새 디렉터리를 사용한다. 원본 DB는 읽기 전용으로 열고 `documents`, `doc_chunks`만
별도 DB로 복사한다. 대화·개인 기억·승인 상태는 복사하지 않는다. 정답 문서 ID가 존재하지
않으면 측정을 중단한다. 실제 `DocumentIndexer.search()`를 사용하므로 임베딩, 동기화,
후보 수, 문서당 청크 제한, RRF, 재정렬의 비용이 포함된다. 모델 장애로 FTS/RRF로 대체되면
평가를 중단한다. 두 경로는 서비스 설정의 차이를 포함하므로 순수 reranker 하나만의 절제 실험은 아니다.

데모 문서 20개·질문 200개를 경로별 3회 측정한다. 질문 순서는 seed=42로 고정하고
질문마다 두 경로 순서를 교대한다. 모델·설정·데이터셋·코퍼스·소스 파일 해시를 기록한다.
초기 색인과 5개 질문 워밍업은 지연 통계에서 제외한다. 측정은 단일 PC에서의 순차 검색이며
동시 사용자 부하 시험이 아니다. 이 수치는 **검색 품질**이며 최종 답변 정확도가 아니다.
실제 서비스의 최대 청크 수를 적용하므로 Recall@10을 보고하지 않는다.

기존 `artifacts/evaluations/benchmark_*`는 해싱 방식의 과거 결과다. 현재 모델 수치와 혼용하지 않는다.
