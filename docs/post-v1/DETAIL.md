# 세부 개발문서 — Post-v1 선택 기능

> 이 폴더의 [README.md](./README.md)에 적힌 내용을 배경·이유·주의점까지 풀어 쓴 세부
> 개발문서다. 설명은 게임 개발 용어에 빗대어 쓴다. 진입 조건과 완료 기준의 단일 기준은
> `README.md`와 기준 문서이며, 내용이 어긋나면 기준 문서를 따른다.
>

## 1. 한 줄 요약

**"이건 나중에"** 폴더다. 하고 싶은 기능들을 v1 핵심 개발에서 떼어내 여기 모아뒀다.
v1의 7일 안정화가 끝나기 전에는 여기 있는 걸 시작하지 않는다.

## 2. 게임으로 치면

**출시 후 로드맵 / DLC 백로그**다.

기획 회의에서 나온 좋은 아이디어들을 "출시 후 검토"로 미뤄놓는 그 목록이다. 이 폴더가
존재하는 목적은 아이디어를 관리하는 게 아니라, **v1 개발 중에 이 기능들이 끼어들지 못하게
막는 것**이다.

스코프 크립이 프로젝트를 죽이는 방식은 게임이든 소프트웨어든 같다. "이것만 하나 더 넣으면
훨씬 좋아질 텐데"가 반복되면 출시가 무한히 미뤄진다.

## 3. 대기 중인 기능들

| 기능 | 하고 싶은 것 | 게임으로 치면 |
|------|--------------|---------------|
| 로컬 AI 고도화 | 여러 모델 라우팅, 모델 교체, 더 큰 컨텍스트 | 렌더링 파이프라인 업그레이드 |
| 임베딩 검색 | 키워드 대신 의미로 기억 검색 | 검색 알고리즘 교체 |
| 외부 서비스 연동 | 캘린더·메일 (읽기 전용부터) | 플랫폼 SDK 연동 |
| 웨이크워드 고도화 | 사용자별 호출어 | 커스텀 입력 바인딩 |
| 피드백 통계 | 좋아요/싫어요 수집 | 텔레메트리 대시보드 |
| 파인튜닝 | 모델을 내 데이터로 재학습 | **최후의 수단** |

## 4. 절대 규칙: 한 번에 하나씩

문서에서 가장 강하게 못 박은 규칙이다.

```text
기능 하나 = 별도 브랜치 + 별도 결정 기록 + 별도 게이트 + 별도 릴리스
```

여러 기능을 한 릴리스에 묶지 않는다. 게임에서 대형 패치에 기능 5개를 같이 넣었다가 뭐가
문제를 일으켰는지 알 수 없게 되는 상황을 막는 것이다.

## 5. 기능별로 조심하는 것

### 임베딩 검색

```text
1. 현재 키워드 검색 정확도를 먼저 기록한다
2. 임베딩 모델·차원·정규화·거리 함수를 결정 기록에 남긴다
3. 모델이 바뀌면 전체 재색인 + 버전 분리
4. 평가셋 정확도가 실제로 올라갈 때만 기본 활성화
5. /forget에서 임베딩 제거 트랜잭션 유지
```

**1번과 4번이 핵심이다.** 새 기술이 좋아 보인다고 그냥 바꾸지 않고, 기존 성능을 먼저 재고
개선이 측정될 때만 채택한다. 게임에서 새 렌더러가 예뻐 보인다고 갈아치우기 전에 프레임을
먼저 재는 것과 같다.

3번도 중요하다. 임베딩 모델을 바꾸면 이전 벡터와 새 벡터를 비교할 수 없다. 좌표계가 달라진
것이라, 전체를 다시 계산해야 한다.

### 외부 서비스 연동

| 규칙 | 이유 |
|------|------|
| 읽기 전용으로 시작 | 쓰기 실수는 되돌릴 수 없다 |
| OAuth 토큰은 자격 증명 관리자에 | 파일에 두면 유출 |
| 서비스 응답은 못 믿는 데이터로 취급 | Phase 3 원칙 유지 |
| 쓰기·전송·초대·메일 발송은 별도 high 위험 기능 | AI가 내 이름으로 메일 보내는 건 심각 |
| 최소 권한 범위와 해지 절차 문서화 | 필요 이상의 권한을 받지 않는다 |

"서비스 응답도 untrusted"가 중요하다. 구글 캘린더라도, **거기 들어 있는 일정 제목은 다른
사람이 쓴 텍스트**다. 초대 메일 제목에 prompt injection을 넣을 수 있다.

### 피드백 통계

- 좋아요/싫어요는 **평가 데이터로만** 저장한다
- 프롬프트나 도구 정책을 자동으로 바꾸지 않는다
- 어떤 응답·어떤 버전에서 나온 통계인지 연결한다

자동 반영을 금지한 게 핵심이다. 게임에서 유저 피드백을 자동으로 밸런스에 반영하면 어떻게
되는지 생각하면 된다. 데이터는 판단 재료지 판단 주체가 아니다.

### 파인튜닝

문서가 **마지막 선택지**로 못 박았다. 조건이 까다롭다.

```text
1. 학습 데이터의 명시적 동의·삭제·익명화·라이선스를 먼저 정의한다
2. RAG·프롬프트·기억 검색으로 해결되지 않는 반복 문제가 있어야 한다
3. 충분한 평가셋이 있어야 한다
4. 운영 시크릿·개인 문서 원문을 학습 데이터로 자동 편입하지 않는다
```

왜 마지막인가? **모델에 학습된 데이터는 지울 수 없다.** RAG나 기억은 레코드를 삭제하면
사라지지만, 파인튜닝된 가중치에서 특정 정보만 빼는 건 사실상 불가능하다.

게임으로 치면 절차적 생성 시스템에 데이터를 하드코딩해서 구워 넣는 것과 같다. 나중에 하나만
빼려면 전체를 다시 굽는 수밖에 없다. 그래서 **먼저 프롬프트와 검색으로 해결을 시도**하고,
그게 안 될 때만 검토한다.

## 6. 새 기능 제안서 양식

새 기능을 하려면 이 양식을 채워야 한다. 게임의 기능 제안서와 거의 같다.

```text
기능명:
해결하려는 문제:
v1로 해결할 수 없는 이유:        ← 이 항목이 관문
사용자 가치:
새 데이터·권한·외부 전송:
설계 변경:
스키마 마이그레이션:
위협 모델 변경:
자동 테스트:
정량 성공 기준:                  ← 감이 아니라 숫자
rollback 방법:
결정 ID:
```

세 번째 항목("v1로 해결할 수 없는 이유")이 필터다. 기존 기능으로 해결되는 문제에 새 기능을
만드는 걸 막는다.

## 7. 진입 조건과 완료 게이트

진입:

- v1 체크리스트 완료
- 7일간 데이터 손상·금지 동작·시크릿 유출 0건
- 기능마다 별도 결정 기록과 위협 모델 검토
- 기존 v1 회귀 테스트를 그대로 유지 가능

완료:

- [ ] 제안 문서와 결정 ID 존재
- [ ] PLAN/DESIGN/SCHEMAS/TESTING 영향 반영
- [ ] v1 전체 회귀 테스트 통과
- [ ] 새 기능 전용 정량 평가 통과
- [ ] rollback·마이그레이션·삭제 경로 검증
- [ ] 위협 모델의 새 High 항목 0건 또는 명시적 출시 차단

**"v1 전체 회귀 테스트 통과"** 가 중요하다. 새 기능이 기존 기능을 깨면 안 된다. 게임 패치에서
신규 컨텐츠를 넣었다가 기존 시스템이 깨지는 걸 막기 위해 회귀 테스트를 돌리는 것과 같다.

## 8. 이 단계에서도 안 하는 것

- 여러 기능을 한 번에 추가
- 사용자 동의 없는 학습 데이터 수집
- 외부 콘텐츠에 권한 부여
- 평가 없이 더 큰 모델로 교체
