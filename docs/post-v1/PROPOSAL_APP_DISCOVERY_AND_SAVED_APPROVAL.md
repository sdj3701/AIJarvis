# 앱 자동 탐색과 최초 실행 승인 저장

작성일: 2026-09-09 · 상태: 구현 및 자동 검증 반영

이 문서는 [동적 앱 제어 제안](PROPOSAL_DYNAMIC_APP_CONTROL_AND_FUNCTION_CALLING.md)의
Gate B를 구체화한다. 기존의 ‘최초 승인은 해당 요청에만 유효’ 정책을 대체한다.
실행 코드는 이 계약을 적용한다. 검증 범위와 실환경 확인 항목은 아래에 구분한다.

## 1. 요구사항과 사용자 흐름

1. 사용자가 ‘카카오톡 실행해줘’처럼 앱 실행을 요청한다.
2. Jarvis가 설치된 앱을 탐색하고 해당 앱을 식별한다.
3. 처음 실행하는 앱이면 ‘카카오톡 실행을 허용할까요? 허용하면 이 앱의 실행 권한을
   저장하고 다음부터 다시 묻지 않습니다.’라고 묻는다. 실제 실행 경로도 함께 표시한다.
4. 사용자가 허용하면 권한을 로컬에 저장하고 앱을 실행한다.
5. 다음 요청부터 같은 앱의 저장된 권한을 확인하고 추가 질문 없이 실행한다.

거절·취소·응답 없음은 실행이나 권한 저장으로 이어지지 않는다. 저장된 권한은 Jarvis와
Windows를 재시작한 뒤에도 유지한다. 권한 저장은 사용자가 요청했을 때 앱을 실행할 수
있다는 뜻이며, 부팅 시 자동 실행이나 Jarvis의 자발적인 앱 실행을 뜻하지 않는다.

## 2. 적용 범위

최초 승인 규칙은 자동 탐색 앱뿐 아니라 기존 app_map 등록 앱에도 적용한다.
app_map은 앱 별칭과 경로를 정하는 용도이며 최초 사용자 승인을 대신하지 않는다.
기존 설정을 자동으로 ‘사용자 승인됨’으로 이전하지 않는다.

승인 저장의 범위는 해당 Windows 사용자와 해당 앱의 **실행**이다.
앱 종료·강제 종료·파일 변경·추가 실행 인자·관리자 실행 권한은 포함하지 않는다.
기존 카카오톡 종료 승인은 그대로 유지한다. 한국어 입력, 슬래시 명령, GUI와 음성에서
동일한 저장소와 실행 정책을 사용한다. 모델 호출 없이도 명시적 명령으로 사용할 수 있다.

## 3. 자동 탐색과 이름 확인

탐색 출처는 사용자/공용 시작 메뉴의 바로가기와 HKCU/HKLM App Paths의 32/64비트 뷰다.
PC 전체 디스크를 재귀 검색하지 않는다. 검증된 exe 대상만 등록하고, 바로가기의 임의
인자·작업 디렉터리를 그대로 실행하지 않는다. 스크립트·셸·URL·제거 프로그램·관리자
도구·해석할 수 없는 링크는 제외한다. Store 앱은 후속 범위다.

카탈로그는 표시 이름·출처·별칭·실행 경로·마지막 확인 시각을 메모리에 보관한다.
파일 정체성은 실행 요청 시 검사해 채운다. 탐색 출처는 Start Menu/App Paths로 제한한다.
같은 실행 파일을 가리키는 여러 바로가기는 하나로 합친다. ‘카톡’은 ‘카카오톡’의
명시적 별칭으로 등록한다. 정규화 후 정확 일치를 우선하고 모호하면 후보를 보여준다.
초기 버전에서는 유사도만으로 앱을 자동 선택하지 않는다.

후보 선택은 실행 승인과 별개다. 이미 승인된 후보를 사용자가 선택하면 바로 실행하고,
미승인 후보를 선택하면 최초 승인 화면으로 넘어간다. 후보 선택만으로 권한을 저장하지 않는다.
후보 티켓은 사용자 요청과 후보 정체성에 묶고, 만료나 대상 변경 시 다시 탐색한다.

카탈로그는 시작 시 읽고 실행 요청에서 필요에 따라 갱신한다. 검색 실패·설치 변경 시
한 번 새로 탐색한다. 캐시는 파생 데이터이므로 지워도 승인 기록은 없어지지 않는다.
캐시 TTL과 항목 상한은 구현 시 설정 계약·테스트와 함께 확정한다.

## 4. 앱 정체성과 저장된 승인

앱 이름만으로 승인 여부를 판단하지 않는다. 최소한 현재 사용자 SID, 정규 exe 경로,
실행 파일 SHA-256을 결합한 대상에 scope=open_app 권한을 저장한다.
승인 기록에는 레코드 ID, 표시 이름, 승인 시각·입력 채널, 승인 당시 파일 정체성을 둔다.
Windows 볼륨/파일 ID는 승인 직후 실행 대상의 바꿔치기를 검사하는 데 사용한다.

같은 이름의 다른 경로, 다른 사용자, 내용이 변경된 실행 파일에는 승인을 재사용하지 않는다.
앱 업데이트로 실행 파일 내용이 바뀌면 ‘앱이 변경되어 다시 승인이 필요합니다’라고 안내하고
한 번 다시 묻는다. 최초 버전은 서명자만으로 업데이트를 자동 신뢰하지 않는다.
이는 변경 없는 앱을 실행할 때마다 다시 묻는 정책과 구분한다.

카탈로그와 별도의 로컬 승인 저장소를 사용한다. 제안 저장 위치는 state 아래 전용 SQLite
파일이며 기존 기억 DB와 분리한다. 실제 경로·DDL·마이그레이션은 구현 전 SCHEMAS에 확정한다.
유일 키는 사용자 SID·정규 경로·실행 파일 해시·scope다. 트랜잭션으로 중복 없이 저장하고,
현재 사용자만 수정할 수 있게 한다. 기억 요약이나 LLM 출력에서 승인 레코드를 생성하지 않는다.

파일 접근이나 저장소 읽기·검증이 실패하면 승인된 것으로 간주하지 않는다.
새 승인 저장에 실패하면 앱을 실행하지 않고 재시도를 안내한다. 손상된 저장소를 자동 초기화해
승인 기록을 조용히 잃지 않는다. 같은 계정 권한으로 PC 자체를 장악한 공격까지 방어하는
저장소는 아니며, 권한 파일을 신뢰할 수 없는 출처에서 복원하지 않는다.

## 5. 승인부터 실행까지

앱 식별 → 저장된 승인 확인 → 필요하면 사용자 최초 승인 → 대상 재검증 → 승인 저장
→ 실행 직전 재검증 → 고정 exe 실행 → 결과 기록 순서로 처리한다.

일회성 승인 티켓과 영구 실행 권한은 구분한다. 티켓에는 exe 경로·해시·파일 정체성·scope를
묶고 한 번만 소비한다. 사용자에게 표시한 대상이 바뀌면 저장과 실행을 중단한다.
모델은 앱 이름만 제안하고, 승인 저장 API나 파일 경로를 직접 선택할 수 없다.

이미 승인된 앱도 실행할 때마다 존재 여부·해시·정책을 확인한다. 셸 없이 검증한 exe만
실행하며 사용자/모델이 임의 인자를 붙일 수 없다. 실행 직전 파일 교체를 막는 Windows
파일 핸들 유지와 공유 모드 검증을 실행 어댑터의 구현·테스트 조건으로 둔다.

승인 저장 이후 OS 실행 실패가 발생하면 ‘권한은 저장됐지만 실행에 실패했습니다’라고
알린다. 앱 정체성이 같으면 재요청 시 묻지 않는다. 실행 성공을 확인하기 전 성공으로 기록하지 않는다.

## 6. 사용자 관리와 취소

GUI에 ‘실행 허용 앱’ 목록과 앱별 ‘허용 취소’를 제공한다. CLI에도 같은 목록 조회와 취소를
제공하되 명령 이름은 구현 단계에서 확정한다. 권한 취소는 현재 실행 중인 앱을 닫지 않고,
다음 실행에서 다시 묻게 한다. 삭제된 앱은 실행 불가로 표시하고 승인 기록은 직접 취소할 수 있다.

승인 대기 중 다른 요청·취소·만료가 발생하면 기존 티켓을 무효화한다. 같은 앱의 동시 요청은
중복 승인 화면과 중복 실행이 생기지 않도록 직렬화한다. 사용자 입력 한 건당 실행은 한 번이다.
승인 직후 크래시가 났더라도 재시작 시 앱을 자동 재실행하지 않는다.

## 7. 구현 작업과 검증 기준

- [x] 앱 카탈로그, 정확 이름/별칭 해석, 후보 선택 구현
- [x] 승인 저장소와 앱 정체성 검증 구현
- [x] app_map 및 자동 탐색 실행 경로를 같은 승인 정책에 연결
- [x] GUI/CLI 최초 승인·허용 목록·허용 취소와 음성 승인 연결
- [x] 사용자 승인 티켓 없이 권한 생성 차단
- [x] Safety Gate, ToolRunner, 감사 기록, 실행 어댑터 연결
- [x] DESIGN/SCHEMAS/TESTING·설정 계약·결정 기록·위협 추적표 동기화

필수 검증 시나리오는 다음과 같다. 자동 검증은 실제 앱 실행 대신 Popen을 대체하며,
Windows 재부팅·실제 카카오톡 기동·마이크 인식·GUI 시각 확인은 별도 수동 확인 대상이다.

| 시나리오 | 기대 결과 |
|---|---|
| 처음 요청한 앱 허용 | 질문 1회, 권한 1건 저장, 실행 1회 |
| 동일 앱 재요청·Jarvis 재시작·Windows 재시작 | 추가 승인 질문 없이 실행 |
| 기존 app_map 앱에 저장된 승인 없음 | 최초 질문 표시 |
| 최초 승인 거절·취소·만료 | 저장 0건, 실행 0건 |
| 동일 이름의 다른 exe·앱 업데이트·경로 변경 | 과거 승인 재사용 0건, 재승인 요청 |
| 승인 이후 파일·바로가기 교체 | 바뀐 대상 실행 0건 |
| 후보가 여러 개 | 자동 선택 0건, 후보 선택 후 승인 여부 확인 |
| 승인 저장 실패·저장소 손상 | 실행 0건, 명확한 오류 안내 |
| 권한 취소 후 실행 요청 | 다시 최초 승인 표시 |
| 외부 문서 또는 모델의 승인 위조 | 권한 저장 0건 |
| 종료·강제 종료 요청 | 실행 승인을 재사용하지 않고 기존 종료 정책 적용 |
| 승인 이후 실행 실패·크래시 | 결과를 구분하고 자동 재실행 0건 |

정적 실행·카카오톡 종료·기존 승인 및 감사 회귀를 함께 통과해야 한다.
동적 탐색을 끄면 app_map으로만 해석하되 이 기능이 적용된 최초 실행 승인 정책은 유지한다.
영구 승인 기능 자체를 비활성화하는 경우에는 실행마다 승인받고, 묻지 않고 실행하는 상태로
되돌리지 않는다. 기능 비활성화나 카탈로그 초기화가 승인 기록 삭제를 뜻하지 않는다.
