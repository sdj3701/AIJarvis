## 4. 폴더 경계가 왜 이렇게 빡빡한가

코드와 실행 데이터는 한 프로젝트 안에서 폴더 역할을 구분한다.

| 경로 | 게임으로 치면 | 규칙 |
|------|---------------|------|
| `D:\Ai\Jarvis` | 프로젝트 소스 | Git으로 관리 |
| `D:\Ai\Jarvis-prototype` | 이전 빌드 백업 | 읽기만. 여기서 개발 안 함 |
| `D:\Ai\Jarvis\data` | **현재 유저 세이브 데이터** | 이전 두 폴더를 통합. Git 제외 |
| pytest 임시 폴더 | 테스트 전용 샌드박스 | 매번 새로 만들고 버림 |

이유는 하나다. **개발 중인 코드가 실제 세이브 데이터를 건드리면 복구가 안 된다.**
게임에서 디버그 빌드가 유저의 클라우드 세이브를 덮어쓰면 어떻게 되는지 생각하면 된다.
여기서 다루는 데이터는 사용자의 실제 대화·기억·개인 문서다.

시크릿(API 키, 백업 암호)도 같은 논리다.

- 운영용 키는 Windows 자격 증명 관리자에만. 파일로 저장 금지
- 개발용 `.env` 파일은 `dev_mode=true`일 때만 읽고, Git에서 제외

`.env`를 커밋했다가 키가 새는 사고는 흔하다. 게임에서 서버 접속 키를 클라이언트 빌드에
박아 넣고 출시하는 것과 같은 실수다.

## 5. DECISIONS.md — 결정 로그 읽는 법

"코드가 대신 결정하면 안 되는 것"만 적는 표다. 상태는 세 가지다.

| 상태 | 뜻 |
|------|-----|
| `decided` | 확정. 이 값을 그대로 쓴다 |
| `pending` | 아직 미정. 이걸 필요로 하는 작업은 시작 금지 |
| `superseded` | 옛 결정. 새 ID로 대체됨 (기존 행은 지우지 않고 남긴다) |

지금 확정된 주요 선택:

| ID | 결정한 것 | 값 | 게임으로 치면 |
|----|-----------|-----|---------------|
| D005 | AI 모델 | Ollama + `qwen3.5:9b`, 로컬 전용 | 렌더링 백엔드 확정 |
| D006 | 웹 검색 | DuckDuckGo (`ddgs`), API 키 불필요 | 무료 미들웨어 채택 |
| D009 | 음성 합성 | Windows SAPI 한국어(Heami), 속도 4 | OS 내장 TTS 사용 |
| D016 | 음성 인식 | 호출어는 Vosk, 질문은 faster-whisper small | 용도별로 다른 미들웨어 |
| D025 | 실행 데이터 통합 | `D:\Ai\Jarvis\data` | 프로젝트 안의 전용 세이브 폴더 |

D007·D008 백업 선택은 완료됐으며 복원 검증은 별도다. D023은 RAG 책임과 답변 정책을 정리한 설계 결정이다.
아직 미정인 선택:

| ID | 미정인 것 | 막고 있는 작업 |
|----|-----------|----------------|
| D024 | 청크·문맥·파일 갱신 세부값 | 개발 기본값 적용; 실무 최적화는 별도 |
| D012 | PDF 파서 | 로컬 텍스트 PDF 지원 적용; OCR은 별도 |
| D013~D015 | 설치 패키징·전역 단축키·자동 시작 방식 | Phase 8 전체 |

**중요한 규칙**: 미정 값을 구현자가 그때그때 대충 정해서 코드에 박지 않는다. 그런 임의
결정이 쌓이면 나중에 "이건 왜 이렇게 되어 있지?"라고 물었을 때 아무도 답을 못 한다.
게임에서 임시 하드코딩 매직 넘버가 출시까지 살아남는 것과 같다.

## 6. REBUILD.md — 지금이 어떤 상황인가

이 프로젝트는 **이미 한 번 만들어 본 프로토타입을 얼려두고, 이해하면서 다시 만드는 중**이다.
게임으로 치면 프로토타입으로 재미를 검증한 뒤 프로덕션 코드로 다시 짜는 단계다.

| 대상 | 위치 | 역할 |
|------|------|------|
| v2 개발 | `D:\Ai\Jarvis`, 브랜치 `main` | 여기서만 새로 만든다 |
| 프로토타입 | `D:\Ai\Jarvis-prototype`, 보관 브랜치 | 소스 확인·비교용 |
| 프로토타입 태그 | Git 태그 `prototype-v1` | 영구 참조점 |

기능 하나를 다시 만드는 순서:

```text
1. 프로토타입에서 그 기능을 직접 써 본다
2. 입력·출력·실패 조건을 짧게 적는다
3. 계약(DESIGN/SCHEMAS)과 테스트를 읽는다
4. 실패하는 테스트를 먼저 추가한다
5. 통과할 만큼만 최소로 구현한다
6. 이 코드가 뭘 하고 뭘 의존하는지 스스로 설명해 본다
7. 문서를 맞추고, 의미 하나만 담은 커밋을 만든다
```

6번이 이 재구축의 목적이다. **"돌아가니까 됐다"가 아니라 "설명할 수 있어야 됐다"** 로
기준을 올린 것이다. 기존 프로토타입 코드는 참고 자료지 정답이 아니다.

## 7. 다 됐는지 확인하는 방법

착수 체크리스트는 이미 전부 통과했다.

- [x] 소스/운영/개발/테스트 데이터 경로를 구분했다
- [x] 운영 데이터가 Git에 안 들어가는 걸 확인했다
- [x] Python 3.11+ 실행 확인 (실제로는 3.13.15)
- [x] 패키지 관리 방식 확정 (`venv` + `pip` + 해시 lock)
- [x] 미정 값을 DECISIONS에 기록했다
- [x] Phase를 건너뛰지 않고 게이트 종료 코드 0으로만 완료 판정하기로 했다

이 체크리스트는 착수 당시 기록이다. 현재 작업은 [PROGRESS](../PROGRESS.md)를 따른다.
2026-10-14 [Phase 3](../phase-03-research/README.md)의 R3 코드·자동 평가를 적용했다. 실장치/릴리스 인수는 별도다.

## 8. 자주 오해하는 것

- "GPU 확인 실패하면 시작 못 하나?" → 아니다. GPU는 Phase 7(음성)에서만 필요하다.
  Python과 D 드라이브 조건만 Phase 0을 막는다.
- "`pending`인 결정이 있으면 아무것도 못 하나?" → 아니다. 지금 Phase 0을 막는 `pending`은
  없다. 각 결정은 자기가 필요한 Phase만 막는다.
- "결정을 바꾸려면 기존 행을 고치면 되나?" → 아니다. 새 ID를 추가하고 옛 행을
  `superseded`로 바꾼다. 결정 이력을 남기는 게 목적이다.
