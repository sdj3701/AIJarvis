# 문서 변경 규칙

문서가 여러 파일로 나뉘어도 같은 사실을 서로 다르게 적지 않기 위한 규칙이다.

## 1. 단일 기준

| 변경 종류 | 먼저 수정할 문서 |
|-----------|------------------|
| 제품 범위·Phase·릴리스 기준 | `PLAN.md` |
| 모듈·인터페이스·의존 방향 | `DESIGN.md` |
| JSON/YAML/SQLite/도구 스키마 | `SCHEMAS.md`와 실제 schema 파일 |
| 테스트 이름·게이트·평가법 | `TESTING.md` |
| 성숙 경로·현재 위치(한 장) | `docs/FLOW.md` |
| 성숙 단계별 목표·진입·다음 연결 | `docs/flow/L*|G*|Ops-*.md` |
| 실제 구현 순서·파일 체크리스트 | 해당 `docs/phase-*/README.md` |
| 사람이 선택해야 하는 제공자·경로 | `docs/00-start-here/DECISIONS.md` |
| 진행 상태·게이트 증거 | `docs/PROGRESS.md` |

## 2. 변경 순서

```text
변경 이유 기록
→ 기준 문서 수정
→ FLOW / flow 세분화 동기화 (성숙 경로·다음 단계가 바뀐 경우)
→ 영향받는 Phase 문서 수정
→ 설정 템플릿/스키마 동기화
→ 테스트 규약과 추적표 동기화
→ PROGRESS 상태 반영
→ 링크·예제 파싱 검증
```

## 3. 금지 사항

- Phase 문서에 기준 문서와 다른 인터페이스를 새로 정의하지 않는다.
- `FLOW.md` / `flow/`에 작업 ID·파일 목록·테스트 이름을 길게 복제하지 않는다.
- `flow/`에 진행 상태 값을 쓰지 않는다. 상태는 `PROGRESS.md`만 갱신한다.
- 행 번호만으로 다른 문서를 참조하지 않는다. 제목·절 이름과 링크를 함께 쓴다.
- 설정 템플릿에 존재하지 않는 키를 Phase 문서에서 사용하지 않는다.
- 테스트가 없는 완료 기준을 추가하지 않는다.
- 미정 값을 구현자가 임의 선택해 확정하지 않는다. DECISIONS에 `pending`으로 남긴다.

## 4. 문서 완료 기준

- 모든 상대 링크가 존재한다.
- JSON 코드 블록은 파싱 가능하다.
- YAML 예제는 설정 모델로 로드 가능하다.
- Phase 0~8 문서가 순서대로 연결된다.
- 요구사항 추적표의 각 행에 테스트가 하나 이상 연결된다.
