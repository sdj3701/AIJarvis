# 문서 변경 규칙

문서가 여러 파일로 나뉘어도 같은 사실을 서로 다르게 적지 않기 위한 규칙이다.

## 1. 단일 기준

| 변경 종류 | 먼저 수정할 문서 |
|-----------|------------------|
| 제품 범위·Phase·릴리스 기준 | `PLAN.md` |
| 모듈·인터페이스·의존 방향 | `DESIGN.md` |
| JSON/YAML/SQLite/도구 스키마 | `SCHEMAS.md`와 실제 schema 파일 |
| 테스트 이름·게이트·평가법 | `TESTING.md` |
| 실제 구현 순서·파일 체크리스트 | 해당 `docs/phase-*/README.md` |
| 사람이 선택해야 하는 제공자·경로 | `docs/00-start-here/DECISIONS.md` |

## 2. 변경 순서

```text
변경 이유 기록
→ 기준 문서 수정
→ 영향받는 Phase 문서 수정
→ 설정 템플릿/스키마 동기화
→ 테스트 규약과 추적표 동기화
→ 세부 개발문서(DETAIL.md)와 개발 흐름(DEVELOPMENT_FLOW.md) 동기화
→ 링크·예제 파싱 검증
```

## 3. 파생 문서

아래 두 종류는 기준 문서에서 파생된 문서다. 여기서 사실을 새로 만들지 않는다.

| 문서 | 역할 | 규칙 |
|------|------|------|
| `docs/*/DETAIL.md` | 세부 개발문서. 같은 폴더 `README.md`의 배경·이유·주의점 | 인터페이스·설정 키·완료 기준을 새로 정의하지 않는다 |
| [`docs/DEVELOPMENT_FLOW.md`](../DEVELOPMENT_FLOW.md) | 작업 ID 단위 전체 순서와 의존 관계 | Phase 문서의 작업 ID·게이트를 복제만 하고 변형하지 않는다 |

원문을 바꾸면 **같은 변경 안에서** 파생 문서도 고친다. 파생 문서만 먼저 고치지 않는다.

## 4. 금지 사항

- Phase 문서에 기준 문서와 다른 인터페이스를 새로 정의하지 않는다.
- 세부 개발문서에 원문에 없는 규칙·기본값·완료 기준을 추가하지 않는다.
- 행 번호만으로 다른 문서를 참조하지 않는다. 제목·절 이름과 링크를 함께 쓴다.
- 설정 템플릿에 존재하지 않는 키를 Phase 문서에서 사용하지 않는다.
- 구현 완료 기준에는 실제 테스트를 연결한다. 설계 단계의 새 사례는 `MISSING`으로 추적하고 구현 완료로 표시하지 않는다.
- 미정 값을 구현자가 임의 선택해 확정하지 않는다. DECISIONS에 `pending`으로 남긴다.

## 5. 문서 완료 기준

- 모든 상대 링크가 존재한다.
- JSON 코드 블록은 파싱 가능하다.
- YAML 예제는 설정 모델로 로드 가능하다.
- Phase 0~8 문서가 순서대로 연결된다.
- 각 폴더의 `README.md`와 `DETAIL.md`가 짝을 이룬다.
- 개발 흐름의 작업 ID 목록이 각 Phase 문서의 구현 순서와 일치한다.
- 요구사항 추적표의 각 행에 테스트가 하나 이상 연결된다.



## 6. 현재 구현·개선 설계·측정 이력의 구분

- 현재 구현은 파일·실제 계약에 근거한다. 개선 설계는 미구현이라고 표시하고 작업/검증 ID를 연결한다.
- 설계 초안에 논리 필드를 쓸 수 있지만 실제 DDL·YAML 키·타입인 것처럼 예제를 만들지 않는다.
- 문서만 개정할 때 설정 파일·DB를 미리 변경하지 않는다. 코드 적용 시 migration·소비자·테스트를 함께 갱신한다.
- 기존 테스트 통과나 과거 benchmark를 새 코드의 완료·품질 증거로 사용하지 않는다.
- 측정 기록에는 버전·소스/자료 해시·명령·범위를 보존한다. 과거 보고서를 새 결과로 덮어쓰지 않는다.
- 문서 완료, 구현 완료, 평가 통과, 릴리스 승인은 각각의 상태로 기록한다.

RAG 적용 사례는 [개정 기록](../rag/RAG_REDESIGN_CHANGELOG.md)과 [추적표](TRACEABILITY.md)를 따른다.
