## 3. TRACEABILITY.md — 요구사항 추적표

R01부터 R26까지 요구사항 하나하나를 이렇게 잇는다.

```text
요구사항 → 설계 문서 절 → 구현 Phase → 검증 테스트 이름
```

예를 보면 바로 이해된다.

| ID | 요구 | 설계 | Phase | 테스트 |
|----|------|------|-------|--------|
| R02 | API 호출 전에 사용자 입력 저장 | SCHEMAS 2·4장 | Phase 1 | 강제 종료 20회 |
| R15 | 승인과 정확한 인자 결합 | DESIGN 10장 | Phase 4 | `test_args_change_invalidates_ticket` |
| R18 | 재시작 후 중복 부작용 0건 | SCHEMAS task_steps | Phase 5 | `test_no_duplicate_write_on_resume` |

### 왜 이런 표를 만드나

게임에서 **"이 기능 삭제해도 되나?"** 를 판단할 때 필요한 표다. 기획서에 있는 요구가 실제로
어느 코드에서 구현되고 어느 테스트로 증명되는지 추적이 안 되면, 리팩토링할 때마다 뭐가
깨지는지 모른다.

규칙 세 개:

- 요구가 추가되면 **설계 항목 1개, Phase 1개, 테스트 1개**를 최소로 연결한다
- 테스트가 없으면 검증 열에 `MISSING`을 적고 **그 Phase 게이트를 통과시키지 않는다**
- 수동 검증만 있는 항목은 자동화할 수 없는 이유와 증거 저장 위치를 적는다

두 번째가 강력하다. **테스트 없는 요구는 게이트를 막는다.** "구현했다고 주장하지만 증명은
없는" 항목이 릴리스에 들어가는 걸 막는다.

## 4. DOCUMENTATION_RULES.md — 문서 관리 규칙

문서가 여러 개로 나뉘면 같은 사실이 서로 다르게 적히기 시작한다. 게임 개발에서 기획서와
구현이 어긋나 있고 위키는 또 다른 얘기를 하는 그 문제다.

해결책은 **어떤 종류의 변경은 어느 문서가 기준인가**를 못 박는 것이다.

| 바꾸려는 것 | 먼저 고칠 문서 |
|-------------|----------------|
| 제품 범위·Phase·릴리스 기준 | `PLAN.md` |
| 모듈·인터페이스·의존 방향 | `DESIGN.md` |
| 저장 포맷 (JSON/YAML/DB/도구 스키마) | `SCHEMAS.md` + 실제 스키마 파일 |
| 테스트 이름·게이트·평가법 | `TESTING.md` |
| 구현 순서·파일 체크리스트 | 해당 `docs/phase-*/README.md` |
| 사람이 선택해야 하는 값 | `docs/00-start-here/DECISIONS.md` |

변경 순서도 정해져 있다.

```text
변경 이유 기록
→ 기준 문서 수정
→ 영향받는 Phase 문서 수정
→ 설정 템플릿/스키마 동기화
→ 테스트 규약과 추적표 동기화
→ 링크·예제 파싱 검증
```

**기준 문서를 먼저 고치고 아래로 내려간다.** 반대로 하면 하위 문서마다 다른 얘기가 남는다.
게임에서 프리팹을 고치지 않고 씬에 배치된 인스턴스만 각각 고치는 것과 같은 문제다.

금지 사항:

- Phase 문서에 기준 문서와 다른 인터페이스를 새로 정의하지 않는다
- 행 번호만으로 다른 문서를 참조하지 않는다 (제목·절 이름과 링크를 함께 쓴다)
- 설정 템플릿에 없는 키를 Phase 문서에서 쓰지 않는다
- 테스트 없는 완료 기준을 추가하지 않는다
- 미정 값을 구현자가 임의로 확정하지 않는다

두 번째("행 번호만으로 참조 금지")가 실무적으로 중요하다. `DESIGN.md 234행`이라고 적으면
문서를 한 줄 추가한 순간 전부 틀린 참조가 된다.

> 참고: `DETAIL.md` 문서들은 **세부 개발문서**다. 기준 문서가 아니므로 여기서 새
> 인터페이스나 설정 키를 정의하지 않는다. 원문이 바뀌면 같은 변경에서 세부 개발문서도
> 함께 고친다.

## 5. THREAT_MODEL.md — 위협 모델

T01부터 T20까지 공격 시나리오를 나열하고, 각각에 대해 네 가지를 적는다.

```text
예방 통제 (막는 방법)
탐지·복구 (뚫렸을 때 아는 방법)
검증 (실제로 막히는지 증명하는 테스트)
상태 (planned / verified / accepted residual / blocked)
```

게임의 치팅 대응 문서와 완전히 같은 구조다. "메모리 조작 → 서버 검증 → 이상치 탐지 → 재현
테스트" 식으로 정리하는 것 말이다.

### 신뢰 경계 그림이 핵심

```text
사용자/마이크
    ↓
로컬 입력·UI ── 승인 경계
    ↓
Orchestrator ── AI 출력 경계 ── AI 모델
    │
    ├── Privacy Gate ── 외부 전송 경계 ── 검색 API/Web
    ├── Memory/Docs ── 로컬 민감 데이터 경계
    └── Safety Gate/Runner ── OS 부작용 경계
```

이 그림 하나가 프로젝트 전체 보안 설계를 요약한다. **경계를 넘을 때마다 검증기가 하나씩
있다.** 게임의 클라이언트-서버-DB 경계마다 검증 레이어를 두는 것과 같다.

핵심 문장은 이것이다.

> 웹, 문서, AI, 도구 출력은 모두 권한 없는 입력이다. 사용자의 명시적 승인만 부작용 권한을
> 부여하며, 승인도 정확한 정규 인자 한 건에만 유효하다.

### 못 막는 것도 적어둔다

v1은 **관리자 권한 공격자나 이미 완전히 장악된 OS로부터 보호하는 제품이 아니다.** 이걸
숨기지 않고 T20에 `accepted residual`로 적어뒀다.

이게 좋은 위협 모델의 특징이다. 게임에서 "클라이언트 메모리 조작은 완전히 막을 수 없다"를
인정하고 서버 검증에 집중하는 것과 같다. 못 막는 걸 막았다고 적으면 대응이 엉뚱한 데로 간다.

## 6. 음성 문서 3개 — 실전 튜닝 기록

이 세 문서는 성격이 다르다. **실제로 안 되던 문제를 고친 기록**이다.

| 문서 | 다루는 문제 |
|------|-------------|
| VOICE_STT.md | 한국어 인식이 엉뚱한 문장으로 나옴 → 엔진 두 개로 분리 |
| VOICE_BARGE_IN_GATE.md | 스피커 소리가 마이크로 들어가서 끼어들기 실패 → 게이트 3단 |
| VOICE_WAKE_COMMAND_UX.md | 호출 오인, 한 문장 명령 불가, "자비스 자비스" 버그 |

게임 오디오 개발과 거의 같은 내용이라, 이쪽 경험이 있으면 읽기 쉬울 것이다. 상세 설명은
[Phase 7 세부 개발문서](../phase-07-voice/DETAIL.md)에 정리했다.

### 이 문서들에서 배울 수 있는 실무 패턴

**1. 기본값과 조정 기준을 같이 적는다**

```text
| 항목 | 기본값 | 조정 기준 |
| 질문 음성 임계값 | -42 dBFS | 말해도 대기면 -45·-48, 잡음이 음성이면 -39·-36 |
```

숫자만 적으면 나중에 아무도 못 만진다. **어느 방향으로 언제 바꾸는지**를 같이 적어야 쓸 수
있는 문서가 된다. 게임 밸런스 값에 "이 값을 올리면 어떻게 되는지"를 주석으로 남기는 것과
같다.

**2. 한 번에 한 값만 바꾸고 같은 입력으로 비교한다**

문서가 반복해서 강조한다. 파라미터 여러 개를 동시에 바꾸면 뭐가 효과였는지 알 수 없다.

**3. 단계적 도입 표를 만든다**

```text
| 단계 | 내용 | 완료 조건 |
| S1 | 게이트 A+B+VAD, 설정, 단위 테스트 | 완료 — 가짜 오디오 오발동 0 |
| S2 | 실장치 스피커 테스트, 임계값 조정 | 성공률 목표 |
| S3 | 필요하면 AEC 실험 | 채택/기각을 결정 기록에 |
```

**S3에 "필요하면"이 붙어 있는 게 중요하다.** AEC는 구현량이 크니까, S2에서 목표가 나오면
아예 안 만든다. 게임에서 최적화 작업을 단계로 나누고 목표 프레임이 나오면 뒤 단계를 안 하는
것과 같은 판단이다.

**4. 왜 안 하는지도 적는다**

AEC와 빔포밍을 미룬 이유가 기술적으로 명확히 적혀 있다.

- AEC: SAPI가 재생 중인 파형 참조를 앱에 안 준다
- 빔포밍: 현재 마이크가 단일 채널이라 배열 정보가 없다

"나중에"만 적으면 나중에 다시 논의가 시작된다. **조건("다채널 마이크 도입 후")을 적어두면
그 조건이 충족될 때까지 논의가 안 열린다.**
