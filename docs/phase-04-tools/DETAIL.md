# 세부 개발문서 — Phase 4 PC 도구

> 이 폴더의 [README.md](./README.md)에 적힌 작업을 배경·이유·주의점까지 풀어 쓴 세부
> 개발문서다. 설명은 게임 개발 용어에 빗대어 쓴다. 인터페이스·설정 키·완료 기준의 단일
> 기준은 `README.md`와 기준 문서이며, 내용이 어긋나면 기준 문서를 따른다.
>
> 전체 순서는 [개발 흐름](../DEVELOPMENT_FLOW.md)에서 본다.

## 1. 한 줄 요약

자비스가 드디어 손발을 갖는다. 앱 실행, 폴더 열기, URL 열기, 메모 파일 생성 **딱 네 개만**.
그리고 **AI가 요청하면 실행되는 게 아니라, 검증 6단계와 사용자 승인을 통과해야 실행된다.**

## 2. 게임으로 치면

이 Phase는 **서버 사이드 검증 파이프라인**을 만드는 것이다.

```text
클라이언트가 "아이템 사용" 패킷 전송
→ 패킷 스키마 검증
→ 인자 정규화 (아이템 ID가 실제 존재하나)
→ 권한/조건 판정 (쿨다운, 레벨 제한)
→ 위험한 작업이면 확인 UI
→ 실행 직전 재검증
→ 로그 남기고 실행
→ 결과 로그
```

여기서 "클라이언트"는 AI다. **AI가 만든 도구 호출 요청은 신뢰할 수 없는 패킷**이다.
Phase 3에서 "외부 텍스트를 못 믿는다"를 했고, 여기서는 "AI 출력을 못 믿는다"를 한다.

## 3. 실행 파이프라인 8단계

```text
AI가 도구 호출 요청
→ 등록된 도구인지 조회
→ JSON 스키마 검증
→ Safety Gate: 경로 정규화 + 위험도 판정
→ 승인 필요하면 여기서 멈추고 "승인 대기" 상태를 값으로 반환
→ 사용자가 승인하면 1회용 티켓 발급
→ 실행 직전 재평가 + 인자 해시 비교 + 티켓 소진
→ 감사 로그에 "이걸 실행하려 한다" 기록 (실행 전에 flush)
→ 제한된 환경에서 실행
→ 감사 로그에 결과 기록
```

### "승인 대기를 값으로 반환"이 왜 중요한가

승인 UI와 실행 코드를 직접 연결하지 않는다. 대신 "승인이 필요하다"는 상태를 데이터로
반환하고, 오케스트레이터가 나중에 이어받는다.

게임으로 치면 UI 버튼의 `OnClick`에서 직접 서버 로직을 호출하지 않고, 커맨드 객체를 만들어
큐에 넣는 것과 같다. 이렇게 해야:

- UI 없이 테스트할 수 있다
- 음성·CLI·트레이 UI가 같은 승인 로직을 공유한다
- **UI가 정책 판정을 우회하는 예외 경로가 안 생긴다**

마지막 항목이 핵심이다. UI에서 "이건 안전하니까 바로 실행"하는 예외를 한 번 만들면 그게
구멍이 된다.

## 4. 규칙별로 "왜 이렇게 하는가"

### 도구는 절대 경로를 안 받는다 (P4-01)

```text
나쁨:   create_file(path="D:\중요폴더\파일.txt")
좋음:   create_file(root="notes", relative_path="메모.txt")
```

도구는 **루트 이름(enum) + 상대 경로**만 받는다. 실제 절대 경로는 설정 파일에만 있고 AI는
모른다.

게임에서 클라이언트가 "이 좌표로 텔레포트"를 보내면 안 되고 "이 포탈 ID 사용"을 보내야 하는
것과 같다. 유효한 목록을 서버가 갖고 있어야 한다.

### 경로에서 거부하는 것들 (P4-01)

| 거부 대상 | 예 | 왜 |
|-----------|-----|-----|
| 상위 이동 | `..\..\Windows` | 샌드박스 탈출 |
| 환경 변수 | `%APPDATA%\...` | 확장 결과가 예측 불가 |
| 절대 경로 | `C:\...` | 루트 지정을 무력화 |
| UNC 경로 | `\\서버\공유` | 네트워크 경로 접근 |
| 장치 경로 | `\\.\PhysicalDrive0` | 디스크 직접 접근 |
| NTFS 대체 스트림 | `파일.txt:숨김` | 숨은 데이터 기록 |
| Windows 예약어 | `CON`, `NUL`, `PRN` | 장치로 해석됨 |
| 끝 공백·점 | `파일.txt ` | 정규화 우회 |

그리고 **경로의 중간 요소마다 reparse point를 검사**한다.

reparse point는 심볼릭 링크나 정션 같은 "다른 곳을 가리키는 폴더"다. `notes` 폴더 자체는
안전한데 `notes\sub`가 `C:\Windows`를 가리키는 정션이면, 최종 경로 문자열만 봐서는 안전해
보인다. 그래서 중간 단계를 다 검사한다.

게임에서 모드 폴더 안의 심볼릭 링크로 게임 실행 파일을 덮어쓰는 공격과 같은 종류다.

### 위험도에 따라 승인 방식이 다르다 (P4-02, P4-03)

| 위험도 | 승인 방식 | 게임에서 같은 것 |
|--------|-----------|------------------|
| low | 승인 없이 실행 | 아이템 장착 |
| medium | y/n 확인 | "정말 판매하시겠습니까?" |
| high | 정해진 문구를 직접 타이핑 | "DELETE라고 입력하세요" |
| forbidden | **승인해도 거부** | 애초에 API가 없음 |

`forbidden`이 중요하다. 삭제·포맷·임의 셸 실행·레지스트리 수정·다운로드 실행은 사용자가
승인하겠다고 해도 실행하지 않는다. **위험한 기능은 확인창을 붙이는 게 아니라 안 만든다.**

도구별 기본 위험도:

| 도구 | 위험도 |
|------|--------|
| `open_app` | low (등록된 앱만) |
| `open_folder` | low (허용 루트 아래 기존 폴더만) |
| `open_url` | low / medium (미등록 도메인은 상승) |
| `create_file` | medium (새 파일) / high (덮어쓰기) |

### 승인 티켓이 인자에 묶여 있다 (P4-03)

이게 이 Phase에서 가장 중요한 방어다.

```text
티켓 = 요청 ID + 도구 이름 + 인자 해시 + 위험도 + 채널 + 만료 시간
```

승인받은 뒤 실행 직전에 **호출을 다시 정규화해서 해시를 비교**한다. 하나라도 다르면 불일치로
처리하고 실행하지 않는다.

왜? 이런 공격을 막는 것이다.

```text
1. AI가 "메모.txt 만들까요?" 요청 → 사용자 승인
2. 승인 사이에 인자를 "중요파일.exe"로 바꿈
3. 티켓은 유효하니까 실행됨   ← 이걸 막는다
```

게임에서 "구매 확인창에는 100원이 표시됐는데 실제로는 10000원이 결제되는" 문제와 같다.
그래서 **확인 화면에 보여준 것과 실제 실행되는 것이 같음을 해시로 증명**한다.

추가 규칙:

- 티켓은 **1회용**이다. 재사용 거부
- 프로세스가 재시작되면 자동 무효
- 음성 채널에서는 high 티켓을 아예 발급하지 않는다 (음성 승인은 위조하기 쉽다)
- Ctrl+C나 타임아웃도 티켓을 폐기한다
- 승인 대기 중 새 입력이 오면 이전 승인을 취소한다

### 감사 로그를 해시 체인으로 잇는다 (P4-04)

```text
각 항목 = 순번(seq) + 내용 + 이전 항목의 해시
```

이렇게 하면 중간 한 줄을 지우거나 고치면 그 뒤 전부의 해시가 안 맞는다. 블록체인과 같은
원리이고, 게임에서 리플레이 로그나 랭킹 기록의 조작을 탐지하는 방식과 같다.

기록 순서도 규칙이 있다.

```text
실행 전:  "이걸 실행하려 한다" (intent) → 즉시 flush
실행 후:  "이렇게 됐다" (result)
```

**의도를 실행 전에 flush하는 이유**는, 실행 중 크래시가 나면 "뭘 하려다 죽었는지"를 알아야
하기 때문이다. 실행 후에만 기록하면 크래시 시 아무 흔적이 없다.

그리고 **거부로 끝난 요청도 반드시 한 줄 남긴다.** 스키마 검증 실패나 정책 거부는
`phase="denied"`와 원인을 기록한다. `execute` 한 번이 감사 로그에 아무것도 안 남기는 경로가
있으면 안 된다. 보안 테스트가 거부 사유를 감사 로그에서 확인하기 때문이다.

일반 대화 내용은 감사 로그에 안 넣는다. 감사 로그는 "무슨 작업을 했나"만 담는다.

### 실행 환경을 최소화한다 (P4-05)

| 금지 | 대신 |
|------|------|
| `shell=True` | 실행 파일과 인자를 배열로 직접 전달 |
| `os.system` | 같음 |
| 문자열로 명령 조립 | 같음 |

문자열로 명령을 조립하면 인자에 `& del *.*`를 넣는 명령 주입이 가능해진다. SQL 인젝션과
완전히 같은 구조이고, 방어법도 같다. **문자열 조립을 안 한다.**

그리고 프로세스에 최소 환경 변수와 고정 작업 디렉터리만 준다. 타임아웃, 출력 크기, 동시
실행 수도 제한한다.

프로세스 종류는 두 가지다.

| 종류 | 동작 |
|------|------|
| `managed_process` | Windows Job Object로 자식 트리를 묶고, 타임아웃 시 전체 종료 |
| `detached_allowlisted` | 등록된 실행 파일을 띄우고 PID만 기록. 앱은 계속 실행 |

Job Object로 묶는 이유는 **자식이 손자를 만들고 죽으면 손자가 고아로 남기** 때문이다.
게임에서 서브프로세스를 띄웠다가 게임을 종료했는데 백그라운드에 계속 남아 있는 문제와 같다.
타임아웃 후 자식 프로세스 0개가 게이트 조건이다.

### Phase 3의 검색 도구도 이 Runner로 옮긴다 (P4-05)

Phase 3에서는 검색 도구를 전용 경로로 실행했다. 이제 그것도 이 Runner를 거치게 한다.

**실행 경로가 두 개 남으면 정책과 감사가 한쪽에만 적용된다.** 게임에서 아이템 획득 경로가
두 개인데 한쪽만 로그를 남기면, 그쪽으로 버그가 새어 나간다.

### 실패를 성공 메시지로 바꾸지 않는다 (P4-06)

`ToolResult.ok=false`와 구체적 오류 유형을 유지한다. "완료했습니다"라고 해놓고 실제로는
아무것도 안 한 게 최악이다. 사용자는 됐다고 믿고 넘어간다.

## 5. 다 됐는지 확인하는 방법

```powershell
python scripts\gate.py --phase 4
pytest -m "phase4 and security"
```

보안 테스트 항목:

- 경로 탈출 모음 전부 거부
- 정션/심볼릭 링크 샌드박스 우회 거부
- `file:`, `javascript:`, 장치 URL 거부
- 로컬호스트·사설 IP·자격증명 URL 거부
- 혼합 문자 도메인(IDN) 정책 검증
- 승인 후 인자·도구명 변경 시 불일치 처리
- 티켓 재사용·만료 거부
- 타임아웃 후 자식 프로세스 0개
- 금지 확장자 생성 0건
- 금지 작업 실행 0건

게이트 통과 항목:

- [x] 허용 앱·폴더 작업 성공
- [x] 비허용 요청 거부와 이유 표시
- [x] medium/high 승인 동작 구분
- [x] 승인 화면과 실제 인자 불일치 실행 0건
- [x] 감사 로그 의도/결과 모두 존재하고 체인이 이어짐
- [x] 타임아웃 프로세스 트리 잔존 0건

## 6. 이번엔 안 하는 것

- 삭제·포맷·임의 셸·레지스트리·다운로드 실행 (영구 금지)
- `run_skill` (임의 스크립트 실행) 활성화
- 한 요청에서 여러 도구 연쇄 실행 (Phase 5)
- UI가 정책 판정을 우회하는 예외 경로
