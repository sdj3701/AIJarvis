# 세부 개발문서 — 운영과 장애 대응

> 이 폴더의 [README.md](./README.md)에 적힌 절차를 배경·이유·주의점까지 풀어 쓴 세부
> 개발문서다. 설명은 게임 개발 용어에 빗대어 쓴다. 실제 운영 명령과 판정 기준의 단일
> 기준은 `README.md`와 기준 문서이며, 내용이 어긋나면 기준 문서를 따른다.
>
> 전체 순서는 [개발 흐름](../DEVELOPMENT_FLOW.md)에서 본다.

## 1. 한 줄 요약

**출시 후 라이브 운영 매뉴얼**이다. 매일/매주/매월 뭘 확인하고, 문제가 터졌을 때 어떤 순서로
대응하는지 적어둔 런북(runbook)이다. v0.5 이후 실제 개인 데이터로 쓸 때부터 적용한다.

## 2. 게임으로 치면

라이브 서비스 게임의 운영 문서다.

- 정기 점검 체크리스트
- 업데이트 배포 절차
- 롤백 절차
- 장애별 대응 매뉴얼 (증상 → 원인 확인 → 조치 순서)
- 유저 데이터 처리 요청 대응

라이브 게임을 해본 적 있으면 이 문서가 왜 필요한지 바로 안다. **장애가 터진 새벽 3시에
판단력으로 대응하는 게 아니라 절차서를 따라가는 것**이 목적이다.

## 3. 운영 원칙 5개

이게 이 문서 전체를 요약한다.

| 원칙 | 게임 운영에서 같은 말 |
|------|----------------------|
| 운영 데이터를 Git·설치 패키지에 넣지 않는다 | 유저 데이터를 빌드 산출물에 섞지 않는다 |
| 문제가 나면 쓰기를 멈추고 원본을 보존한 뒤 **복사본에서** 조사한다 | 장애 DB를 직접 만지지 않고 스냅샷을 떠서 조사 |
| DB 무결성이나 감사 체인이 실패하면 PC 도구를 끈다 | 이상 감지 시 결제·거래 기능부터 차단 |
| **백업 성공이 아니라 복원 성공이 기준** | 백업이 돌았다고 복구 가능한 게 아니다 |
| 시크릿 유출이 의심되면 로그 삭제보다 **키 폐기를 먼저** | 키를 무효화하고 나서 조사한다 |

마지막 항목이 특히 중요하다. 유출을 발견했을 때 반사적으로 로그를 지우고 싶어지는데,
**로그를 지우면 어디까지 샜는지 조사가 불가능해진다.** 키는 폐기하면 그 순간 무해해지지만,
범위 조사는 로그가 없으면 영원히 못 한다.

## 4. 시작·종료 순서

시작:

```text
1. 단일 인스턴스 락
2. 설정·스키마 버전 검증
3. 임시/격리 파일 점검
4. SQLite 무결성 검사
5. 미완료 세션·작업 점검
6. 감사 로그 마지막 해시 확인
7. 입력 활성화
```

종료:

```text
1. 신규 요청 중단
2. 진행 중인 안전한 작업만 완료하거나 취소
3. 승인 티켓 폐기
4. 체크포인트와 종료 이벤트 기록
5. 오디오·프로세스·DB 정리
6. 단일 인스턴스 락 해제
```

**입력을 마지막에 활성화**하는 것과 **신규 요청을 먼저 차단**하는 것이 핵심이다. 게임 서버의
graceful shutdown과 같다. 신규 접속을 막고, 진행 중인 처리를 마무리하고, 그다음에 내린다.

강제 종료 뒤에는 **다음 시작에서 복구 결과를 확인하기 전에 같은 작업을 다시 지시하지 않는다.**
Phase 5의 중복 실행 방어를 사람이 무력화하지 않기 위한 규칙이다.

## 5. 정기 점검

### 매일

```powershell
python scripts\gate.py --integrity
```

확인: DB 무결성, 미완료 작업, 감사 체인, 예산 80% 경고, 보존 정책 결과, 최근 오류.

게임 운영의 일일 대시보드 확인과 같다.

### 매주

```powershell
python scripts\backup.py create
```

확인: 암호화 아카이브 생성, 별도 위치 복사와 해시 확인, 오래된 사본 정리, 평문 임시 파일
잔여 0건.

### 매월

```powershell
python scripts\backup.py restore --archive <latest> --target <empty-test-root>
```

확인: 새 경로 복원, 무결성 검사, 기억 검색 1회, 설정 로드, 원본 로그 유효성, 결과 기록.

**매월 복원 훈련이 이 문서에서 가장 중요한 항목이다.** 백업은 매주 돌아가고 있지만, 실제로
복원해 보지 않으면 복원이 되는지 알 수 없다. 게임 업계에서 "백업은 있었는데 복원이 안 됐다"는
사고는 실제로 자주 일어난다.

## 6. 업데이트 절차

```text
1. 정상 종료하고 백업을 만든다
2. 릴리스 매니페스트와 현재 앱/스키마/프롬프트/설정 버전을 비교한다
3. 새 코드를 별도 가상환경에 설치한다
4. 마이그레이션 dry-run 결과를 확인한다
5. 테스트 데이터 경로에서 전체 게이트를 실행한다
6. 운영 DB의 추가 백업 사본을 만든다
7. 마이그레이션 후 앱을 한 번 시작하고 무결성을 확인한다
8. 문제가 없을 때만 자동 시작을 다시 켠다
```

포인트는 **백업이 두 번 나온다**는 것(1번, 6번)과 **dry-run**(4번)이다.

dry-run은 마이그레이션을 실제로 적용하지 않고 "이렇게 바뀔 것이다"만 보고하는 것이다.
게임에서 DB 마이그레이션을 스테이징에서 먼저 돌려보고 영향 범위를 확인하는 것과 같다.

## 7. 롤백 절차

| 롤백 대상 | 조건 |
|-----------|------|
| 코드만 | DB 스키마가 이전 코드와 호환될 때만 |
| DB | 업데이트 직전 백업을 **새 경로에 복원**하고 검증 후 데이터 루트를 전환 |
| 설정 | 이전 설정의 스키마 버전이 현재 코드와 맞을 때만 |
| 프롬프트 | 프롬프트 버전과 모델 ID를 함께 기록 |

**운영 DB 위에 이전 DB를 덮어쓰지 않는다.** 새 경로에 복원해서 검증하고, 그다음에 가리키는
경로를 바꾼다.

이유는 두 가지다. 복원이 실패하면 현재 상태까지 잃는다. 그리고 **실패 원인을 조사할 원본이
사라진다.** 게임 운영에서 장애 DB를 덮어쓰면 사후 분석이 불가능해지는 것과 같다.

## 8. 장애별 대응

### 설정 오류 (종료 코드 2)

```text
1. 사용자 운영 설정을 보존한다
2. 예제 설정과 키 이름·스키마 버전을 비교한다
3. default: deny를 완화해서 우회하지 않는다
4. 수정 후 설정 해시가 바뀐 이유를 기록한다
```

3번이 중요하다. **막혀서 안 되는 걸 정책을 풀어서 통과시키지 않는다.** 게임에서 검증 로직에
걸린다고 검증을 끄는 것과 같은 유혹인데, 그러면 원인이 남아 있는 채로 방어만 사라진다.

### SQLite 무결성 실패 (종료 코드 5)

```text
1. 앱과 자동 시작을 중단한다
2. 손상된 DB를 읽기 전용 사본으로 보존한다
3. 최신 백업을 새 위치에 복원한다
4. 복원본의 무결성과 기억 검색을 확인한다
5. 복원본을 새 데이터 루트로 전환한다
```

손상된 DB를 먼저 보존하는 게 순서상 2번이다. 손상된 파일에서도 일부 데이터는 건질 수 있고,
원인 분석에도 필요하다.

### 감사 체인 실패

```text
1. PC 도구를 전부 비활성으로 시작한다
2. 끊긴 순번 전후 파일을 보존한다
3. 로그 회전·동시 실행·수동 수정 여부를 확인한다
4. 원인이 밝혀지고 새 체인 시작점이 기록될 때까지 기능을 재활성화하지 않는다
```

감사 체인이 깨졌다는 건 "무슨 일이 있었는지 증명할 수 없는 상태"다. 그 상태에서 PC를 조작하는
기능을 켜두면 안 된다. 게임에서 부정행위 로그가 유실됐을 때 거래 기능을 먼저 잠그는 것과
같은 판단이다.

### 실행 중이던 단계 발견

```text
1. 작업, 도구, 인자 표시, 의도 로그, 변경 경로를 사용자에게 보여준다
2. 자동 재실행하지 않는다
3. 실제 결과를 확인해서 성공/실패/취소 중 하나로 마감한다
4. 필요하면 새 작업으로 다시 요청한다
```

Phase 5의 `running` 상태 복구 규칙이 운영 절차로 나온 것이다.

### API 장애·예산 초과

- 진행 중인 로컬 저장을 완료한다
- 신규 요청을 중단한다
- 재시도 한도 이후 사용자에게 원인과 미완료 단계를 표시한다
- **예산을 자동으로 늘리지 않는다**

마지막 항목이 정책이다. 예산 초과를 자동 증액으로 해결하면 예산이 존재하지 않는 것과 같다.

### 시크릿 유출 의심

```text
1. 해당 키를 제공자에서 즉시 폐기·재발급한다
2. PC 도구와 외부 전송을 비활성화한다
3. 로그·기억·백업을 탐지 패턴으로 조사한다
4. 노출 경로와 시간 범위를 기록한다
5. 새 키를 자격 증명 관리자에 저장한다
6. 재현 테스트를 추가한 뒤 기능을 재활성화한다
```

순서가 정확히 이 순서여야 한다. **키 폐기가 1번, 조사가 3번, 로그 삭제는 아예 없다.**
6번의 "재현 테스트 추가"도 중요하다. 같은 경로로 다시 새지 않는다는 증거 없이 기능을 다시
켜지 않는다.

## 9. 사용자 데이터 작업

| 작업 | 방법 | 주의 |
|------|------|------|
| 기억 조회 | `/memory list` | 후보와 확정을 구분해서 볼 것 |
| 기억 삭제 | `/forget <id>` | tombstone과 인덱스 제거 확인 |
| 기억 내보내기 | `/memory export` | 민감도 필터와 저장 위치 승인 |
| 원본 로그 삭제 | 보존 정책 또는 전용 관리 명령 | 활성 세션 파일은 삭제 금지 |
| 전체 초기화 | **v1에서 자동 기능으로 제공하지 않음** | 백업 후 수동 절차 필요 |

전체 초기화를 자동 기능으로 안 만든 이유는 명확하다. **되돌릴 수 없는 파괴적 기능을 버튼
하나로 만들지 않는다.** 게임에서 계정 삭제를 즉시 실행하지 않고 유예 기간을 두는 것과 같은
판단이다.
