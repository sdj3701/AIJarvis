> 이 폴더의 [README.md](./README.md)에 적힌 작업을 배경·이유·주의점까지 풀어 쓴 세부
> 개발문서다. 설명은 게임 개발 용어에 빗대어 쓴다. 인터페이스·설정 키·완료 기준의 단일
> 기준은 `README.md`와 기준 문서이며, 내용이 어긋나면 기준 문서를 따른다.
>
> 전체 순서는 [개발 흐름](../DEVELOPMENT_FLOW.md)에서 본다.

## 1. 한 줄 요약

**아무 기능도 없는데 절대 안 깨지는 빈 프로젝트**를 만든다. AI 호출도, 검색도, PC 조작도
없다. 켜고 끄고, 설정 읽고, 세이브 폴더 만들고, 로그 쓰는 것까지만 한다.

## 2. 게임으로 치면

새 프로젝트를 만들고 아래를 먼저 세팅하는 단계다.

- 프로젝트 세팅 파일 로드와 검증
- 세이브 폴더 생성과 마이그레이션
- 세이브 파일이 도중에 깨지지 않게 하는 원자적 저장
- 게임 중복 실행 방지 (mutex)
- 로그 시스템과 크래시 리포트 개인정보 필터
- 실행하면 검은 화면에 커서만 뜨는 상태

**"재미없는 것부터 먼저 만든다"** 가 이 Phase의 전부다. 이걸 나중에 하면 이미 쌓인 기능
전부를 다시 손대야 한다.

## 4. 규칙별로 "왜 이렇게 하는가"

### 설정에 모르는 키가 있으면 실행 거부 (P0-02)

```text
extra="forbid"  →  설정 파일에 정의 안 된 필드가 있으면 로드 실패
```

`enemySpeed`를 `enemeySpeed`로 오타 냈는데 엔진이 조용히 기본값을 쓰면, 며칠 뒤에
"밸런스 패치가 왜 안 먹지?" 하고 헤매게 된다. 그래서 **오타는 조용히 넘기지 않고
즉시 죽인다.**

같은 이유로 이런 것들도 거부한다.

- 설정 버전이 코드보다 높으면 거부 (구버전 클라이언트가 신버전 세이브 읽는 상황)
- `tools.default = allow`로 바꾸면 거부 (권한 기본값은 항상 "금지")
- 데이터 루트 밖을 쓰기 경로로 지정하면 거부 (샌드박스 탈출)
- 컨텍스트 배분 비율 합이 100%를 넘으면 거부 (메모리 버짓 초과)

### 설정 해시를 계산해서 로그에 남긴다 (P0-02)

설정 세 파일을 정규화해서 해시 하나로 만들고 시작 로그에 찍는다. 게임에서 버그 리포트에
빌드 넘버와 설정 버전을 같이 받는 것과 같다. **"내 PC에선 재현이 안 되는데요"** 를 줄이는
장치다.

### 시계와 난수를 직접 읽지 않는다 (P0-04)

```text
나쁨:   지금 시간 = 시스템 시계 직접 호출
좋음:   지금 시간 = 주입받은 Clock에게 물어봄
```

`DateTime.Now`를 코드 곳곳에서 직접 부르면 테스트에서 "3일 뒤"를 만들 수 없다. 게임에서
`Time.deltaTime` 대신 자체 타임 서비스를 두고 일시정지·배속·리플레이를 지원하는 것과
완전히 같은 이유다. 난수도 같다. 시드를 주입할 수 있어야 재현이 된다.

대기(sleep)도 마찬가지로 주입한다. 그래서 재시도 백오프 테스트가 실제로 5초를 기다리지
않고 즉시 끝난다.

### ID는 `접두어_ULID` 형식 (P0-04)

ULID는 **정렬 가능한 GUID**다. 그냥 GUID는 정렬하면 순서가 뒤죽박죽인데, ULID는 앞부분이
시간이라 문자열 정렬만으로 시간순이 된다. 로그를 뒤질 때 이게 크게 편하다.
접두어(`req_`, `ses_`)를 붙이는 건 로그에서 이 ID가 뭔지 바로 보이게 하려는 것이다.

### 세이브를 임시 파일에 쓰고 바꿔치기한다 (P0-07)

```text
임시 파일에 쓴다 → flush → fsync → 원본 이름으로 교체(os.replace)
```

세이브 도중 전원이 꺼지면 어떻게 되는지 게임 개발자면 다 안다. 원본에 직접 쓰면 반쯤 쓰인
파일이 남아서 다음 실행에 로드 실패한다. 그래서 **완성된 임시 파일을 통째로 교체**한다.
교체 자체는 OS가 원자적으로 처리해 준다.

`fsync`는 "OS 버퍼에만 있지 말고 진짜 디스크에 써라"는 명령이다. 이게 없으면 파일은 만들어
졌는데 내용이 비어 있는 상황이 생긴다.

### 시작할 때 깨진 파일을 격리한다 (P0-07)

지난번에 크래시가 났다면 `.tmp` 파일이나 마지막 줄이 잘린 로그가 남아 있다. 이걸 그냥 읽고
죽는 대신 `state/quarantine`으로 옮기고 "이런 걸 격리했다"고 기록한다.

게임에서 손상된 세이브 슬롯을 백업으로 돌리고 유저에게 알려주는 것과 같다. 조용히 지우면
원인 조사가 불가능해진다.

### 두 번째 실행을 막는다 (P0-07)

`state/jarvis.lock` 파일을 OS 파일 락으로 잠근다. 두 번째 프로세스는 안내 메시지와 종료
코드 1로 끝난다.

같은 DB를 두 프로세스가 동시에 쓰면 데이터가 깨진다. 게임 클라이언트를 두 번 띄우면 세이브가
망가지는 것과 같은 문제라서, 아예 실행을 막는 게 정답이다.

### 로그에 개인정보를 안 남긴다 (P0-06)

로그를 쓰기 전에 반드시 마스킹 필터를 통과시킨다. API 키, Bearer 토큰, 개인키, 주민번호
패턴이 로그에 원문으로 남으면 안 된다.

크래시 리포트에 유저 이메일과 결제 토큰이 그대로 들어가서 문제가 되는 사례와 같다.
**필터를 나중에 붙이면 이미 남은 로그는 못 되돌린다.** 그래서 로그 시스템을 만들 때 같이
만든다.

### 로그는 append + flush 순서로 쓴다 (P0-06)

한 줄 덧붙이고 즉시 flush한다. 버퍼에 모아뒀다가 통째로 쓰면 크래시 때 마지막 몇 줄이
사라진다. 마지막 몇 줄이 바로 크래시 원인이 담긴 줄이다.

### bootstrap을 두 번 돌려도 결과가 같아야 한다 (P0-05)

멱등성(idempotent)이라고 부른다. 폴더가 이미 있으면 건너뛰고, 설정 파일이 이미 있으면
**절대 덮어쓰지 않는다.** 사용자가 조정한 설정이 재설치로 날아가면 안 된다.

게임 패치가 유저 설정 파일을 초기화해 버리는 사고와 같은 맥락이다.

### DB 스키마를 여기서 실제로 실행해 본다 (P0-05)

문서에 적힌 DB 스키마(DDL)는 아직 한 번도 실행된 적이 없다. 그래서 이 작업에서 같이
확인한다.

- SQLite 버전이 3.34 미만이면 전문 검색 기능이 없으니 명확한 에러로 알린다
- 트리거 6개가 실제로 만들어지는지 확인한다
- 레코드를 `candidate → confirmed → superseded → deleted`로 전부 굴려 보고 검색 인덱스
  무결성 검사를 통과시킨다

**스키마 오류를 Phase 2에서 발견하면 그때까지 쌓은 기억 데이터를 다 버려야 한다.**
그래서 여기서 미리 굴려 본다. 게임에서 세이브 포맷을 확정하기 전에 마이그레이션 테스트를
먼저 하는 것과 같다.

### 조립은 한 곳에서만 (P0-08)

`wiring.py` 한 파일에서 설정·시계·ID 발급기·로그 라이터를 다 조립한다. 나머지 코드는
필요한 걸 주입받는다. 싱글톤을 아무 데서나 `Instance`로 끌어다 쓰지 않고 조립 지점을
한 곳으로 모으는 것과 같다. 테스트에서 가짜 구현을 꽂아 넣기 쉬워진다.

## 5. 다 됐는지 확인하는 방법

```powershell
python scripts\bootstrap.py     # 데이터 폴더·설정 사본·DB 준비
python -m app                   # 실행 (입력하면 그대로 되돌려줌)
python scripts\gate.py --phase 0   # 자동 통과 판정
```

게이트가 종료 코드 0이면 통과다. 확인 항목:

- [ ] 예제 설정 3개가 정상 로드된다
- [ ] `default: allow`와 모르는 설정 키가 거부된다
- [ ] 테스트 로그에 시크릿 원문이 0건이다
- [ ] bootstrap을 두 번 돌려도 기존 설정을 덮어쓰지 않는다
- [ ] 두 번째 인스턴스가 거부된다
- [ ] 깨진 파일이 격리되고 복구 결과가 기록된다
- [ ] DB 스키마·트리거가 적용되고 검색 인덱스 무결성 검사가 통과한다
