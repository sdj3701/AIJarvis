## 1. 어떤 부분을 왜 바꿨는가

| 부분 | 변경 | 이유 |
|---|---|---|
| 문서 청크 | 재귀 v4, 같은 장의 짧은 조문 최대 4개 packing | 짧은 조문을 작은 청크로만 흩뜨리지 않으면서 조문별 원문 위치 유지 |
| 긴 조문 검색 | 뒤쪽 조각과 같은 조문의 첫 청크를 함께 검색 문맥에 추가 | 뒤쪽 호만 읽어 처벌 조건·형량·주체를 잃는 문제 완화 |
| 인용문 | 모델이 원문 ID 선택 → 앱이 저장 원문을 붙임 | 생략 부호·위치 메타데이터가 원문에 섞이거나 인용을 다시 쓰는 오류 방지 |
| 조항·페이지 | 인용문에 해당하는 SourceSpan으로 앱이 표시 | 모델에게 조항/페이지 숫자 작성을 맡기지 않음 |
| 열거된 호 | 같은 파일·장·조·항의 제공된 '각 호' 전제를 별도 인용 | '심의한다' 같은 동사나 적용 조건을 누락하지 않기 위해 |
| 복합 질문 | 항목별 검색 → 결과 교차 배치 → question_id별 검증 | 한 질문의 숫자를 다른 질문에 사용하거나 뒷질문 근거가 잘리는 문제 방지 |
| 질문 대상명 | 제공 원문에 있는 대상명을 답변에 썼지만 인용에는 없으면 거부 | 다른 호의 원문으로 정당화하는 오류 차단 |
| 후속 질문 | 이전 사용자 문맥과 현재 질문을 검증 입력에서 분리 | 과거 질문까지 다시 답해야 한다고 오해해 올바른 답을 보류하던 문제 수정 |
| 입력 예산 | 검색 답변 전용 프롬프트 | 일반 대화/도구 설명 때문에 실제 근거를 버리는 문제 개선 |
| 검증 실패 | 최대 1회 재생성 후 동일 검증, 실패하면 보류 | 오류를 그대로 출력하지 않으면서 수정 가능한 인용 선택 오류 복구 |

`scripts/app/rag/passages.py`는 인용 후보를 만든다. `grounding.py`는 원문/위치/숫자/계산과 항목별 주장을 검사한다.
`research.py`는 질문별 근거를 모으고 `loop.py`는 입력 예산·생성·검증·재시도 사용량을 관리한다.
`chunker.py`와 `indexer.py`는 각각 짧은 조문 묶기와 긴 조문 전제 검색을 맡는다.

## 2. 처리 순서

```text
PDF → 페이지 텍스트·좌표 → 반복 머리말/꼬리말 제거 → 구조화 Markdown
    → 같은 장의 짧은 조문 묶기 / 긴 조문 재귀 분할
    → 384토큰 상한 검사 → 원문·페이지 구간·벡터 저장

질문 → 현재 질문/이전 문맥 분리 → 필요한 경우 하위 질문 준비
    → 하위 질문마다 전체 query 임베딩·검색·재정렬
    → 조문 앞부분·인접 문맥 보충 → 중복 제거·입력 예산 적용
    → 모델이 답변 및 원문 ID 선택 → 앱이 원문·조항·페이지 연결
    → 질문별 인용/주장 검증 → 통과한 답변 표시
```

문서 청커와 질문 준비는 별도다. 질문을 글자 수에 맞춰 문서처럼 잘라 저장하지 않는다.
복합 질문 분해는 현재 물음표 구분과 “A와 B는 각각 …” 형태를 처리한다. 임의의 모든 접속문을 이해하는 분류기는 아니다.
복합 질문은 최대 4개다. 당시 claim 상한은 4개였으며 답변 품질 후속 변경에서 최대 16개로
늘렸다. 입력 한도 안의 근거로 확인하지 못하면 보류한다.

짧은 조문 packing은 개별 조문 구간이 문자·토큰 상한의 1/4 이내일 때만 적용한다.
합친 구간도 전체 상한을 지키며 다른 장을 넘지 않는다. 제목만 있는 청크는 계속 제외한다.
이번 실제 건축기본법은 조건에 맞는 묶음이 없어 **34청크, 최대 381토큰**으로 이전과 같다.

## 3. 실제 출력 예

복합 질문 “건축정책기본계획의 수립 주기와 건축정책 국회보고 주기는 각각 몇 년인가요?”에
계획은 **5년 — 제10조 제1항·PDF 2쪽**, 보고는 **2년 — 제15조 제1항·PDF 4쪽**으로 별도 답한다.
각 답변 아래 실제 조문 인용을 붙인다. 제14조처럼 전제와 호가 페이지를 걸치면 3쪽과 4쪽을 각각 표시한다.
페이지는 원본 PDF의 1부터 시작하는 쪽 번호다. 출처 링크의 page는 청크 범위,
`위치:`의 page는 해당 인용문 범위이므로 둘이 다를 수 있다.

## 4. 수정 전후 시험

같은 PDF·같은 12질문을 각각 2회 실행했다. 동일 로컬 Qwen/임베딩/재정렬 모델과 384/48토큰 설정을 사용했다.

| 지표 | 수정 전 재귀 | 수정 후 재귀 |
|---|---:|---:|
| 내용 정답 또는 올바른 보류 | 16/24 | 24/24 |
| 내용 + 맞는 조항 원문 인용 + 페이지 포함 | 14/22 | 22/22 |
| 위 조건 + 조항 번호도 표시 | 0/22 | 22/22 |
| 잘못된 확정 답변 | 1 | 0 |

인용/표시 지표는 답이 존재하는 11질문×2회다. 내용 지표는 없는 벌금액을 묻는 2회의 올바른 보류도 포함한다.
화면에 출력된 인용 28개를 저장 Markdown과 원본 페이지 구간으로 재대조하여
원문 일치·조항·항·페이지를 확인했다. 명시적인 조·항·페이지 요청 2질문도 별도 통과했다.

| 필수 사례 | 실제 검사 결과 |
|---|---|
| TC 1 초대형 조문 | 가상 제1조를 5개로 분할. 2·3번째 조각에만 있는 대상을 질문. 검색 2위/1위, 대상 인용·전제·형량 답변 2/2 |
| TC 2 짧은 조문 | 가상 제2~5조를 한 청크로 묶음. 조문별 질문 모두 1위 검색, 올바른 조문/페이지 답변 4/4 |

제공 법률에는 초대형 벌칙 조문이 없어 TC 1·2는 명시적으로 표시한 별도 **가상 PDF**를 사용했다.
가상 자료를 건축기본법 내용으로 취급하거나 실제 법률 답변 점수에 합산하지 않았다.
자동 Phase 0~3/보안 회귀 **545개 통과**, 화면·음성/프롬프트 회귀 별도 **34개 통과**,
기존 실제 모델 회귀 **17/17**을 확인했다. 두 자동 테스트 묶음에는 일부 중복이 있다.

백업: `D:\Jarvis-v2-dev\backups\pdf-citations-20261015-4dbe6ad0`. **21문서·54청크**, 최대 381토큰, 미측정 토큰 0개, DB 무결성 ok,
반복 sync 변경 0건이다. 원본 Downloads PDF는 수정하지 않았다.
실행 중인 개발 앱은 완전히 종료하고 다시 시작해야 새 소스를 읽는다. 정식 exe 릴리스 빌드는 이번 검증 범위가 아니다.

같은 모델의 검증에는 의미 판단 오류가 남을 수 있다. PDF OCR·복잡한 표·임의의 복합 문장,
문맥 상한보다 더 큰 전제/여러 조문은 별도 검증이 필요하다. 제목/인용 위치가 확인됐다는 사실과
법률 판단의 완전성을 구분한다. 이번에는 법률 해석을 확장하지 않고 제공 PDF 안의 사실을 대조했다.
