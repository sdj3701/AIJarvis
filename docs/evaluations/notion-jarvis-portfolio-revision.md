## 상세 페이지 · 01 · 문서 검색 개선

**단일 검색 방식의 결과를 비교하고, 두 검색 순위를 결합해 상위 결과의 품질을 높였다.**

### 문제 정의

로컬 문서에서 답변의 근거를 찾기 위해 검색 방식을 선택해야 했다. 검색 결과가 존재하는지만으로는 충분하지 않아, 관련 문서가 상위 몇 개 결과 안에 포함되는지와 얼마나 높은 순위에 배치되는지를 함께 평가했다.

### 원인 분석 · 설계 판단

FTS5는 토큰 매칭과 BM25를 사용하고, 현재 벡터 검색은 단어·문자 n-gram을 512차원으로 해싱한 뒤 코사인 유사도를 계산한다. 두 방식은 문서에 부여하는 점수와 순위가 다르므로, 원점수를 단순 합산하기보다 각 검색의 순위를 결합하는 방법을 선택했다.

현재 벡터화는 학습된 신경망 임베딩 모델이 아닌 특징 해싱 방식이다. 따라서 이 비교는 해당 구현의 결과이며, 일반적인 의미 임베딩 모델의 성능 비교로 해석하지 않는다.

### 해결 방법

1. 동일한 문서와 질문으로 Vector Search, SQLite FTS5(BM25), Hybrid RRF를 비교할 수 있는 독립 벤치마크를 구성했다.
2. 두 검색 결과의 순위를 RRF로 결합했다. 검색 경로별 별도 가중치는 없으며, 스무딩 상수 k=60을 사용했다.
3. 벤치마크의 하이브리드 검색은 각 경로에서 반환 수의 5배까지 후보를 요청한 뒤 융합 결과를 top_k개로 제한한다. 실제 후보 수는 문서 수에 제한된다.
4. Recall과 MRR로 검색 품질을, 평균·P95로 지연 시간을 함께 확인했다.

RRF 점수 = 각 검색 경로의 1 / (60 + 해당 문서의 순위)를 합산

벡터 검색 → FTS5 검색 → RRF 순위 결합 → 상위 결과 반환

현재 벤치마크는 두 검색을 순차 실행한다. 비동기 병렬화·캐싱·고비용 리랭커 제거를 통한 속도 개선은 이 결과에서 검증한 항목이 아니다.

## 상세 페이지 · 03 · 검색 품질과 지연 시간 평가

**Recall@5 89% → 91% · MRR@5 0.751 → 0.820**

벡터 단독 검색과 비교해 관련 문서의 상위 5개 포함 비율과 정답 순위가 개선됐다. 평균 검색 시간은 1.029ms에서 1.057ms로 소폭 증가했다.

### 동일 조건 비교 · top_k=5

| 검색 방식 | Recall@5 | MRR@5 | 평균 검색 시간 | P95 검색 시간 |
|---|---:|---:|---:|---:|
| Vector Search | 89.0% | 0.751 | 1.029ms | 1.330ms |
| SQLite FTS5 | 69.0% | 0.658 | 0.049ms | 0.075ms |
| Hybrid RRF | **91.0%** | **0.820** | 1.057ms | 1.191ms |

Recall@5는 관련 문서 중 상위 5개 결과에 포함된 비율이며, MRR@5는 첫 정답의 순위 역수를 평균한 값이다. 두 지표 모두 높을수록 좋다. P95는 측정값의 95번째 백분위수다.

### 평가 조건

- 측정일: 2026.09.14
- 데모 문서 20개·청크 20개, 평가 질문 200개
- 질문 유형: keyword 67개·semantic 67개·hybrid 66개
- 방식별 질문 10개 워밍업 후 질문당 5회 반복
- 반환 결과 수 top_k=1·3·5·10을 각각 평가했으며, 위 비교표는 top_k=5 결과
- RRF 스무딩 상수: k=60
- 시간 범위: 질의 벡터화·인덱스 생성·LLM 답변 생성을 제외한 검색 단계
- 벤치마크 벡터 검색은 문서 벡터를 미리 계산해 메모리에 보관하고 전체 후보의 코사인 유사도를 계산

### 결과 해석

이번 평가에서는 Hybrid RRF의 Recall@5와 MRR@5가 가장 높았고, FTS5의 검색 시간이 가장 짧았다. Hybrid RRF는 벡터 단독보다 평균 검색 시간이 약 0.029ms 늘었지만 Recall@5는 2.0%p, MRR@5는 0.069 상승했다. 검색 품질과 추가 지연 비용을 함께 확인한 결과다.

P95 검색 시간은 벡터 1.330ms, Hybrid 1.191ms로 측정됐다. 다만 평균 시간과 변화 방향이 다르고 별도의 최적화 전후 실험이 아니므로, 이를 병렬 처리나 특정 최적화의 효과로 단정하지 않는다.

### 그래프 설명

- **평가 질문 수에 따른 누적 평균 Recall@5:** 모든 방식에 동일한 질문 순서(seed=42)를 적용했다. 질문이 추가될 때까지의 평균을 보여주며, 질문 증가에 따른 모델 학습이나 성능 향상을 뜻하지 않는다.
- **검색 결과 수에 따른 Recall:** top_k=1·3·5·10의 실측 결과를 연결했다. 반환 결과 수에 따른 변화를 보여준다.
- **검색 품질·지연 시간 비교:** 동일한 top_k=5 실행의 Recall@5·MRR@5와 평균·P95 검색 시간을 함께 제시한다.

### 평가 범위

소규모 데모 평가이므로 실제 사용자 질문이나 대규모 문서 환경으로 일반화하려면 추가 검증이 필요하다. 독립 검색 벤치마크의 측정값이며, 애플리케이션 전체의 응답 시간이나 LLM 답변의 정확도·환각 감소를 평가한 결과는 아니다.

## 상세 페이지 · 04 · 배운 점과 다음 단계

AI가 작성한 코드를 학습 내용과 비교하고, 실제 구현과 측정 결과를 확인하며 개선 방향을 정했다. 검색 방식의 이름만으로 효과를 판단하기보다, 동일한 평가 조건에서 검색 품질과 지연 비용을 함께 비교하는 과정이 중요하다는 점을 배웠다.

다음 단계는 실제 사용자 질문으로 정답 매핑을 검토하고, 문서 규모를 늘려 검색 품질과 지연 시간을 다시 측정하는 것이다. 이후 학습된 임베딩 모델과의 비교 및 구간별 시간 측정을 바탕으로 필요한 최적화를 선택할 계획이다.
